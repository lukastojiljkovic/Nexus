## Wave entries

### Two advisories with no fix to move to (2026-10-05)

The English pull request's dependency audit failed on a lockfile it had not
touched: two advisories reached the audit feed after the public-release pull
request's last green run, and neither names a patched release.

**`braces` ≤ 3.0.3 (GHSA-vfj7-8cjw-p6xm) was removed, not excused.** It came in
through excalidraw > sass@1.51.0 > chokidar@3, which puts it on the shipped
side, where this repository allows no exceptions. excalidraw ships its styles
compiled and nothing here runs Sass, so an override raises sass to 1.79.4. The
1.79 line is the first on chokidar 4, which dropped glob support and `braces`
with it, and 1.79.4 is the last before sass took `@parcel/watcher`, a native
dependency with a build script that would have added a second prebuild to the
package. The shipped set lost eleven packages, and the third-party notices
were regenerated.

**`http-cache-semantics` ≤ 4.2.0 (GHSA-ch52-4w7c-c8xp) is tolerated in the
toolchain scan.** It is build-time only, in the cache in front of
electron-builder's Electron download, and the advisory needs a cache shared
between users serving a zeroed `Set-Cookie`. 4.3.0 appeared the same day and
falls outside the advisory's range, but its diff never touches the max-stale
path, so an override to it would have silenced the scan and fixed nothing.
The allowance carries that reasoning and what retires it.

### The interface's numbers follow the language too (2026-10-04)

The bilingual pass of 2026-10-02 translated the words; this one translates the
figures and finishes the shipped catalogues. It closes §4.1 item 7 — the forty
hand-written `Intl.DateTimeFormat` constructions in twenty-seven files that
[[DC-145]] measured on 2026-09-26.

**One door to `Intl`.** `intl.ts` is now the only renderer module that builds an
`Intl` object (the lone survivor is `strings.ts`'s `Intl.PluralRules`, which is
what `dayUnit`/`countUnit` are). It exposes memoised `dateTimeFormat`,
`numberFormat` and `collator` factories plus `lowerCase`/`upperCase`, and it
derives the grouping and decimal characters from `Intl` itself rather than
hard-coding them, so a value prefilled into an edit field parses back in either
language. The factories key their cache on the ACTIVE LOCALE *and* the options,
not the options alone: a formatter cached under Serbian must not answer after
the switch, and every module is evaluated before `applyStoredLocale` runs, so a
module-scope constant would be Serbian for the life of the process. The
expected strings in `localeEnglish.test.ts` are `Intl`'s own output for
`en-GB`, not a hand-written template.

**The catalogues carry English.** The 426-entry food table gained `nameEn`,
`labelEn` on every serving and `notesEn`, merged by a text-preserving script so
ids, numbers, sources, key order and line endings stayed byte-identical;
`food.ts` validates the English fields the way `catalogue.test.ts` validates the
Serbian ones, and the renderer picks a field through `fitnessLocale.ts`, with
`searchFoods` matching either language. The electronics catalogue's 153 entries
gained `nameEn`/`summaryEn` (and the handful of Serbian pin labels `labelEn`),
picked by `elecLocale.ts`, with `elecCatalogue.ts` searching both; the exercise
catalogue already carried `nameEn`. `generateRosPackage` and `generateSketch`
take a `GeneratedLanguage` and write English README/Python/`.ino` prose when
main's locale is English. `demo/business.ts` now carries the same `EN` map the
other seeders do, which closes §4.1 item 13. `applyLocale` also rewrites
`<html lang>`, and the web shell does it at first serve — `index.html` ships
`lang="sr"`, and the module corrects it from `globalThis` without a DOM lib.
The temporary merge/fetch scripts at the repository root were removed before
hand-off, as their own headers said they would be.

**The screenshots are English now.** The harness takes `--locale=en`; until
then every automated run was pinned to Serbian whatever the machine spoke. The
README's and the website's five images were re-shot with it, and looking at
them found the two things no test had: one Serbian payee in the English ledger,
„Taksi/prevoz", which has no diacritic for the diacritic test to catch, and an
electronics bench that opened on a different circuit, because the list sorts
by name and the English names sorted differently. The English names now keep
the Serbian order, and a test pins it.

**Verified on 2026-10-04**, on a Windows host, with every gate CI runs:
`pnpm install --frozen-lockfile`, `pnpm build`, typecheck across all 13
packages, lint (no errors; the two pre-existing hook warnings), `test:wall` 77
of 77, all 26 static gates, and every suite — core 6 157 tests over 128 files,
desktop 2 434 over 131, db 2 304 over 69, ui 106, web 62 and the five sync
packages. The first full run failed three cases of `apps/desktop`'s `demo/study.test.ts`
on Vitest's 5 000 ms default while turbo ran the core suite beside it; alone,
the same cases take about 0.6 s each. Each opens a real encrypted database and
runs every migration, the cost `packages/db` met first and answered with a 20 s
`testTimeout`, and `apps/desktop` now takes the same.

**The tree 1.4.0 is tagged from was packaged again on 2026-10-05.** `dist`
built an unsigned `Nexus-Setup-1.4.0.exe`, the six fuses read back as
configured, and the executable, started on a throwaway `--user-data-dir`,
opened its window and wrote its profile there while the real profile's newest
write time stayed where it was.

### The interface becomes bilingual (2026-10-02)

English joins Serbian as a language the product actually serves. The commit
before this one (`f957f86`) had written the English sub-tables — every
`devtools`, `electronics` and professional-toolkit surface — and this pass
finished the job: the main table, the locale machinery, the prose the core
package generates, the copy the main process composes, the web shell, and the
demo profile's own content.

**The table is the compiler's problem, not a reviewer's.** `strings.en.ts` is
3 648 leaves, one for every leaf of `strings.sr.ts`, declared `as const` so
`strings.ts` can check the whole object against `Strings` — the shape widened
from the Serbian source. A leaf left untranslated or a key invented is one
compile error each. The record is written as `LOCALES: Record<Locale, Strings>`
with `Locale = "sr" | "en"` written out, because `keyof typeof LOCALES` over two
full tables made the declaration emitter refuse to serialize the type (TS7056);
the written-out union keeps drift impossible, since a code missing from it or
from the record is still a compile error.

**First run follows the system language, and the test that pinned the old
behaviour was passing by accident.** `readStoredLocale()` now answers `sr` when
the system locale starts with `sr` and `en` for anything else, and a stored
value stays authoritative from then on — including a stale value, which falls
back to `DEFAULT_LOCALE` rather than re-asking the question. The old test
asserted "nothing stored answers Serbian" and passed on this machine only
because a Serbian Windows reports `sr-Latn-RS` as `navigator.language`; on CI
it would have answered `en`. The test now stubs `navigator` explicitly, and the
non-Serbian case is a test of its own.

**The main process has to be told, because it cannot read the renderer's
storage.** Native file dialogs and OS notifications are composed in main, in a
separate bundle with no access to `localStorage`, so the renderer reports the
language it is serving on a new `locale:set` channel — a report, not a request,
like `profiles:set-active`, with the payload re-validated against the two codes
and nothing but the next sentence written in it. `main/locale.ts` holds the
answer; `shellStrings.ts` and `notificationStrings.ts` became per-locale tables
read at call time, so a constant can no longer freeze whichever language was
active when the module loaded. A real launch seeds it from `app.getLocale()`
before the renderer speaks; an automated run (`--shots`, `--demo`) keeps the
Serbian default its output is pinned to.

**Prose the core package generates got English counterparts rather than a
second copy of the logic.** `@nexus/core/devtools/datetime` already produced
Serbian sentences for cron expressions, relative times and durations; it now
exports `explainCronEn`, `formatRelativeEn` and `formatDurationEn` beside them,
and `explainCron`/`formatRelative`/`formatDuration` pick by the caller's locale.
Core has no locale state and does not reach for the renderer's — the drawer
passes `activeLocale()` in.

**The demo profile seeds English content when the interface is English.**
`DemoContext` carries the locale, `seedDemoProfile` takes it from
`mainLocale()`, and each seeder translates the values a person reads — task
titles, note bodies, habit names, study material, people, documents, events,
budgets — while the Serbian path stays byte-identical, the `demoRandom` streams
keep their exact draw order, and ids, slugs and enum values are left alone. The
business half (`business.ts`, seeded only by the `--demo` CLI) is the one seeder
this pass did not reach; it is recorded in `STATUS.md` §4.1.

**Two things found on the way were defects of the copy itself.** The committed
English sub-tables gave the product a wrong name in 96 places, from a stale note
in the scratch brief that the task's own rule overrides: the product is `Nexus`
in every language, and every occurrence is corrected. And one English file kept a
Serbian `„` where the English copy needs `“`, which `check:quotes` had no reason
to look for in a table it did not yet scan.

**The web shell got the same rule, in miniature.** `apps/web/src/strings.ts`
keeps its Serbian table and gained an English one applied at import when the
stored choice is `en` or the system language is not Serbian; the web shell has
no settings row yet, so the answer is resolved once per page.

**Everything in the sandbox passed**: `pnpm typecheck` 13/13, `pnpm lint` 14/14
with no errors, all 26 `check:*` gates, `pnpm test:wall` 77/77, the desktop
suite 128 files / 2 409 tests, and the core, db, web, ui and root-script suites
green. `pnpm build` and `smoke` need Electron and esbuild and run outside this
sandbox, as the release checklist already says.

**Two of the failures met on the way were the checkout, not the code.** A
Windows checkout with `core.autocrlf=true` writes CRLF into the working tree,
which broke two things that read the bytes rather than the content: the static
pgTAP meta-tests mutate a fixture with `replace(/\nrollback;\n/, …)`, and
Vite's transform of `apps/desktop/scripts/render-notices.mjs` leaves a stray
`\r` behind its shebang. Both files are normalised to LF in the working copy,
which git does not even see on a text file. That held for one working copy
only, and the next checkout failed the same way; since 2026-10-04 the
meta-tests read their fixtures through `readLf`, and `.gitattributes` pins the
two shebang scripts to LF, so a fresh Windows checkout passes as CI does.

### Preparing the public open-source release (2026-10-02)

One long pass over everything a stranger needs before this repository can be
made public under Apache-2.0. The checklist was the open-source readiness audit
written the day before (its changes are in pull request #39); its §7 and §8 now
carry the status of every line of it.

**The licence premise went first, because it is what made other things false.**
ADR-087 supersedes ADR-080 §1 — the "commercial, closed-source" premise — and
says explicitly that the notice obligation is untouched, because that obligation
belongs to the dependencies' licences and binds an open-source binary exactly as
it bound a closed one. ADR-080 keeps its words and gains a banner, the rule this
repository already follows for accepted ADRs.

**Two files were still describing a proprietary product, and neither was in the
list.** The Gentoo ebuild declared `LICENSE="all-rights-reserved"` with a note
about the `EULA` group, and its README told the user to add an
`ACCEPT_LICENSE` line — for a package that is now Apache-2.0 and therefore
accepted by default. Portage would have refused a free package. The
`grep` in the brief was for the words *commercial*, *closed-source* and
*proprietary*; the ebuild said none of them. Both are fixed, and the README
now tells an existing Gentoo user that their old `package.license` line is
unused.

**The full-history secret scan was clean, and that is a measurement rather than
a hope.** gitleaks 8.24.3 — the same version `security.yml` pins — downloaded
to a temp folder and its SHA256 checked against the official checksums file,
then run over every commit: **no findings**. The working-tree scan reports
things only under `apps/desktop/out/`, `apps/desktop/release/` and
`supabase/.temp/`, all git-ignored build output and the local development
stack's own generated secrets. No `.env` file has ever been committed, no
suspicious path (`secret`, `credential`, `.pem`, `.p12`, `.pfx`, `.key`) exists
anywhere in history, and every `supabase.co` in the tree is a placeholder
(`PROJECT.supabase.co`, `abc.supabase.co`) or a link to Supabase's own
documentation.

**The documents that were written are the ones a maintainer normally avoids.**
`SECURITY.md`, `CONTRIBUTING.md` (with the DCO recommendation and the English
locale position), `CODE_OF_CONDUCT.md` — Contributor Covenant 2.1 taken
verbatim from the official markdown, with only the enforcement contact filled
in — `PRIVACY.md`, `TERMS.md`, `SUPPORT.md`, `ROADMAP.md` and `CHANGELOG.md`.
Every factual sentence in `PRIVACY.md` was read out of the code rather than
assumed, and one of them was wrong in the first draft: the terms page said
content is encrypted with XChaCha20-Poly1305, which is what a comment in
`wrap.ts` mentions as the alternative; the tree actually uses **AES-256-GCM**
(`AEAD_KEY_BYTES = 32`) with X25519 for key agreement and Argon2id plus
HKDF-SHA256 for derivation.

**The release pipeline is written and has never run.** `release.yml` builds on
`windows-latest` and `ubuntu-latest` from a `v*` tag, refuses a tag that does
not match `apps/desktop/package.json`, renders the third-party notices from
`licences.json` after `check:licences` proves they still describe the tree,
generates a CycloneDX SBOM, writes `SHA256SUMS`, attests build provenance, and
uploads a **draft** release. CodeQL, dependency review and Scorecard are wired
with `if: !github.event.repository.private`, the pattern `pages.yml` already
uses, so they switch themselves on with the visibility change instead of
failing on a private repository that has no Advanced Security licence. All four
workflows are actionlint-clean.

**One piece of the pipeline is a new script with a test.** The notices a release
has to carry are not a file in the repository; they are rendered from
`licences.json` by `apps/desktop/scripts/render-notices.mjs`, whose test pins the
property that matters — the fence around each notice is computed from the text,
because a licence containing three backticks would otherwise close its own
code block early and turn the rest of the document into prose.

**The name check is a recommendation the founder has not taken.** "Nexus" has
121,545 repositories on GitHub, a package on npm, a project on PyPI, twelve
winget matches including one literally named `Nexus`, and Sonatype's artifact
repository manager has used the name for around fifteen years. EUIPO TMview
refused the connection from this machine, and WIPO's Global Brand Database and
the Serbian register are browser applications with no query API, so the register
search is **not done** — the name-check record said so rather than implying
otherwise (it was moved out of the repository on 2026-10-02), and it carried
four alternatives whose availability was actually checked on GitHub, npm, PyPI
and winget.

**What could not be tested, stated plainly:** the release workflow (needs a
tag), the `database` CI job (needs Docker and Supabase; left to CI), and the
Gentoo ebuild (needs portage and a published tarball). `make verify` was not run
as a single command because GNU make is not installed on this machine; every
command it runs was run individually, and all of them are green.

**The packaging path was then proved locally, after the paragraph above was
written.** `pnpm --filter @nexus/desktop dist` was run on Windows from this
tree: it finished in **79 seconds**, produced `Nexus-Setup-1.3.0.exe`, and
`dist.mjs`'s own closing check passed — „win32-x64.node is the only prebuild in
the package". Three things it settled that had until then been read in the
source rather than measured against a real build:

- **The installer is genuinely unsigned.** `Get-AuthenticodeSignature` reports
  `NotSigned`, with no signer certificate. So `TERMS.md`, `SECURITY.md` and the
  website are right about the SmartScreen warning, and nothing in this
  repository claims a signature it does not have.
- **`release/win-unpacked/` really does carry `LICENSES.chromium.html`**, which
  is the claim ADR-080 §7 makes and could only check once, on 2026-08-02.
- **A THIRD distinct size for the same version.** The build produced
  183 277 915 bytes, against the delivered 183 821 644 and the 183 821 582 of
  the second `eceb07e` build. That is the non-reproducibility finding in
  STATUS §4.4, now with three data points rather than two, and all three from
  the same version number.

The delivered artefact was restored afterwards, so
`release/Nexus-Setup-1.3.0.exe` is still the byte-identical 183 821 644-byte
file that shipped. (Its `.blockmap`, a 190 KB build by-product of the fresh
build, was removed in the same step; any `dist` run regenerates it.)

### The fuses and the housekeeping schedule (2026-10-02)

**Three known gaps, closed, and one attempt withdrawn.**

- **The packaged executable is hardened with Electron fuses.** `electron-builder`
  26.15.3 supports `electronFuses` (app-builder-lib drives `@electron/fuses`),
  so the config names them at packaging time: `RunAsNode` off, `NODE_OPTIONS`
  off, CLI inspect off, cookie encryption on, embedded asar integrity on, and
  only-load-from-asar on. `GrantFileProtocolExtraPrivileges` stays on, with the
  reason in the file: the renderer still loads from `file://`. The 1.3.0
  installer's own executable was read back and had every one of them wrong —
  `RunAsNode` Enabled, `EnableNodeOptionsEnvironmentVariable` Enabled,
  `EnableNodeCliInspectArguments` Enabled, `EnableCookieEncryption` Disabled,
  `EnableEmbeddedAsarIntegrityValidation` Disabled, `OnlyLoadAppFromAsar`
  Disabled — which is the state this config changes. **A fresh read-back could
  not be produced in this environment**: see the sandbox note below.
- **The README's `FORCE` section matches the migration.** `…090300` *attempts*
  `force row level security` on `storage.objects` and `realtime.messages` and
  always fails on Supabase (`must be owner of table objects`, verified against a
  live Postgres 17), because both are owned by platform service roles. What is
  applied is the policies, and `00_rls_enabled.test.sql` asserts the honest
  invariant. §6.5 now says that instead of claiming the force lands.
- **The housekeeping schedule is a migration.** `…090000_housekeeping_schedule`
  creates `pg_cron` if it can, unschedules by name, and schedules
  `public.nexus_sync_housekeeping()` hourly; if the extension cannot be
  installed on a hosted project the migration warns with the exact dashboard
  step and schedules nothing rather than aborting the deploy.
- **Revocation still does not end the GoTrue session.** A migration that
  deleted the `auth.sessions` row from an AFTER UPDATE trigger on
  `public.devices` was written and withdrawn the same day. Deleting from `auth`
  needs a `security definer` function, and `03_catalog_surface.test.sql`
  asserts that no such routine exists in `public` or `private`; CI's `database`
  job failed on exactly that assertion. The rule stands, so the end state stays
  the one `supabase/README.md` §6.2 names: the admin sign-out API, called from
  an authenticated Edge Function.

**PR #39's leftovers.** The QR fixture's Serbian mobile number (`+381 64 123
4567`, and `064123456` in the SMS and vCard cases) became an obviously
fictional `+381 60 000 0000` / `060000000`, with every expectation updated. Seven
working documents left the repository — the open-source readiness audit, the
name check, the DC-42 findings list, the sync-hardening specification, the
landing-page PRD and the founder's raw specification with its module
elaborations — and every Markdown link to them was removed or rewritten; the
dated PRD, research and prompt documents that cite them as inputs keep the
citation, and `docs/README.md` says why.

**The website is rebuilt in the same brochure system as the other Windows-app
pages.** `site/site.css` is byte-identical to `Refreshify`'s, the Archivo fonts
replace Geist, the accent stays the app icon's gold (`#8a6410` light,
`#e5bf62` dark), the copy is English with every factual claim carried over, and
the links point at `lukastojiljkovic/Nexus` and
`lukastojiljkovic.github.io/Nexus/`. `sitemap.xml` and `llms.txt` were
updated. The existing Pages workflow already deploys `site/`, so no new one was
added. Checked with Playwright at 1440×900 and 390×844 in both themes (measured
`scrollWidth` equal to the viewport at both widths; fonts loaded; every image
resolved): screenshots in the session's scratch directory.

**An environment note, because it explains the missing fuse read-back.** The
managed sandbox denies the directory listing esbuild uses to resolve an absolute
path, so `pnpm build`, `pnpm --filter @nexus/desktop dist` and any Vitest run
that loads a config file fail at startup with
`Cannot read directory "../../../..": Access is denied` — before a line of
application code runs. Every suite, typecheck, lint and static gate was still
run (the config-bearing suites through Vitest's Node API with `config: false`
and the same options their config files set), and the pnpm store index had to be
repaired with `pnpm store add` before `check:licences` could read it. The one
gate that could not run at all on this machine is the packaged build, so the
fuse read-back and the launch check are the first thing to do on a normal
Windows host or in CI.
