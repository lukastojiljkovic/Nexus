## Part 1 — the wave entries (STATUS §3)

### E4a — the circuit writes its own sketch (2026-08-31)

Founder: *„Nastavi dalje sta treba, web/sync je za sada trajno na hold-u, dok ne
zavrsimo sve feature za desktop, lako cemo ih posle portovati na sajt jer je
electron osnova."* So: the desktop, and the next thing on it is ADR-085's E4.

E4 is scoped in the ADR as four things — *„Arduino sketch, ROS 2 package,
URDF/SDF, export to disk"*. This entry is the first and the fourth. The second
is next; the third is blocked on a decision only the founder can make, and is
written up as a question in STATUS §5 rather than guessed at.

**The honest boundary is the whole design.** `packages/core/src/electronics/
sketch.ts` emits the WIRING: a `constexpr` for every board pin a peripheral is
actually wired to, the `pinMode` each of them needs, `Wire.begin()`/`SPI.begin()`
where the board's own bus pins carry the bus, and a `loop` that reads every
input back to the serial monitor so a person at the bench can see whether the
thing is really connected the way the canvas says. It does **not** emit the
program. „Read the distance and stop the motor under 20 cm" is a decision nobody
but the user has made, and a generator that invented one would hand back a guess
wearing the authority of generated code.

That line is not modesty, it is the only line that can be drawn without
fabricating: everything above it is derived from the catalogue's pin functions
and from `buildNets` — the same derived model the rules engine reads, which is
ADR-085 §2's reason for putting E3 first — and everything below it would have to
be invented. Three narrower refusals fall out of the same rule:

- **A pin whose part declares a `library` is left entirely alone.** No
  `pinMode`, no read. A DHT22's DATA line is neither an input nor an output; it
  is both, in a timed sequence the library owns, and a `digitalRead` on it
  returns noise wearing the shape of a reading.
- **Libraries are named, never `#include`d.** The catalogue's `library` field
  holds a *Library Manager* name — „DHT sensor library" ships `DHT.h`, and no
  rule takes you from the first string to the second. The sketch lists what to
  install, in the form the user types into the IDE. `Wire.h` and `SPI.h` are the
  two exceptions, because those are the core's own and their names are facts.
- **No output is ever driven.** Only pins the board listens to are read; a servo
  swept or a relay closed by a program nobody wrote is a machine acting for no
  reason.

**The catalogue grew the field that makes a refusal possible.** `ComponentDef`
now carries `programming: "arduino" | "linux"`, **required on a board and
forbidden on everything else**, and all ten boards declare it. It is required
rather than optional because „absent" and „linux" would reach the generator as
the same answer, so the eleventh board somebody adds would be silently
unprogrammable instead of loudly incomplete. The Pico is `"arduino"`: it is an
RP2040 you upload a compiled binary to, and the `arduino-pico` core builds
sketches for it exactly as the AVR core does. The two Raspberry Pis are
`"linux"` and get a refusal — a `.ino` for a Pi 4 is not a worse answer than a
Python file, it is an answer to a question nobody asked.

**Refusing is a first-class answer, not an error.** `no-board`, `many-boards`
and `not-programmable` come back as values. „This circuit has two boards" is a
true and useful sentence, and a thrown exception would make the panel choose
between showing nothing and showing a stack. The dialog opens on a refusal too
and says which one it is; what the refusal removes is „Sačuvaj kao…", not the
explanation.

**Two processes generate, and only one writes.** `generateSketch` is pure, so
the renderer calls it for the preview and main calls it *again* for the file.
`elec:export-sketch` takes a profile id and a circuit id and nothing else: main
reads its own rows, generates its own text, and writes it at a path the native
save dialog returned. The renderer never supplies a filesystem path (SEC-EL) and
never supplies the bytes either — what lands on disk is the circuit as stored,
not as a renderer described it. `handleIcsExport` is the shape this follows.

**Then the screenshot said the generator was wrong (DC-88).** The new sweep
scene photographed the demo profile's own circuit — an HC-SR04 on a UNO — and
the file in the frame opened `#include <SPI.h>`, called `SPI.begin()`, named
neither pin and ended with „no pin is read here". Every test passed.

The rule that was wrong: **one end's CAPABILITY was read as the wiring's
INTENT.** D10 and D11 on a UNO are `spi-cs` and `spi-mosi`, and they are also
two ordinary digital pins, which is where a person wires TRIG and ECHO. The
catalogue had written the correct rule down three months earlier, beside the
same board's analogue block — „A4 and A5 double as the I²C pair — the ambiguity
that makes „is this an analogue input or the bus?" a question about the wiring,
not the pin" — and the generator asked it about the pin.

**The blast radius was a second module.** E3's `bus-role` rule filters to pins
that „commit to a bus role" and judges the pairing, and it counts a *board's*
role as a commitment. So a BMP280 bit-banged onto D11 — legitimate, and the
exact practice that rule's own comment says is ordinary — was reported as a
crossed bus, at severity **error**. Fixed once, where it belongs: one
`pinBuses(pin)` in `component.ts`, and both modules intersect the two ends
through it. The sketch treats a wire as a hardware bus only where both ends
share one; the rules engine judges two pins as crossed only when they are on the
**same** bus and badly paired.

Both fixtures now carry D11, with a comment saying why — a hand-written fixture
is trimmed to what the test needs, and a pin's second name is exactly what gets
trimmed away.

**And the escape that was missing.** Every name the sketch prints comes from
outside it: a part label is any string up to 120 characters and a circuit name
any up to 200, bounded in length and in nothing else. A label carrying a
star-slash would have closed the header comment early and turned the rest of the
connection table into code. One `commentSafe` now spaces every adjacent star and
slash, in either order, and collapses newlines. Its own doc comment had to spell
the pair out in words — written literally, it ended that comment, which is how
the escape got tested before the test was written.

**Three smaller things found while reading, none of them the feature.** The two
`circuitProblems`/`circuitRules` calls in `ElectronicsPage.tsx` were inline in
the JSX, so every keystroke in the notes box re-derived the nets and all
thirteen rules; they are `useMemo` on the document now, and the sketch joined
them rather than adding a third full derivation per render. `busesUsed` computed
a `uart` field nothing read — an unused field is a question, and the answer was
that a device on the board's hardware UART shares the port with the serial
monitor, which the sketch now says out loud above `Serial.begin`. And
`sketch.test.ts` had a fixture typed `kind: "input"`, which is not a
`ComponentKind`; Vitest does not typecheck, so it was green while
`pnpm typecheck` was red.

**And three more found by reading the finished file rather than by running it.**
`Sketch.connections` was a public field nothing on screen read — the same shape
`check:pro-flags` was written for, one level up: a table the generator computed
and only its own test consumed. It is now the dialog's wiring table, printed
above the code, with the „—" row for a pin the sketch deliberately does not name
and one sentence under the table explaining why one exists — which is the thing
a person actually reads while pushing a jumper in, and nobody counts pins out of
a C comment one-handed. `serialLabel` fell back to the *board pin's* own label
when a part's name folded away to nothing, and a board pin's label is catalogue
text: one quote in it would end the C string literal it lands in. It falls back
to the constant now, which `slugify` built out of `[A-Za-z0-9_]`, so the hole is
closed by there being nothing unsafe left to fall back to. And `loop` wrote
`${entry.read ?? ""}` over a list already filtered to entries that have one — a
`??` whose other branch emits `(PIN_X)`, which is not C; a type guard makes the
branch unrepresentable, the same way `isNamed` already did one line above.

The sweep gained a **second** scene for the dialog, because the first one
photographs the plain shape. „Merenje razdaljine" is an UNO and an HC-SR04: no
libraries, no unnamed pin, and therefore two whole sections of the panel that no
frame measured. The new scene switches to the demo's other circuit — a DHT22,
whose DATA line the library owns — and photographs the loaded shape.

**That scene then produced DC-89 on its first run, which is the second time in
one wave a screenshot said something no test could.** The probe waited for „Kod"
to stop being `disabled` and clicked it, and the frame came back as the ordinary
page with no dialog on it. `disabled` was a true reading of a *stale* state:
selecting a circuit only schedules the page's effect, so for one turn the button
is still enabled on the OUTGOING document — the click opened the dialog, and the
effect that ran a moment later did exactly its job, which is to drop a dialog
belonging to the circuit that just closed. The class is general: `!disabled`,
`!== null`, „the element exists" are properties of whatever state is current, and
a wait that would also pass on the old page is not a wait.

The repair that suggests itself — wait for the TRANSITION, require the button to
be seen disabled before believing an enabled one — ran and reported „found
nothing to open" six times out of six, which is the better half of the lesson:
`setDoc(null)` and the `setDoc(opened)` behind a sub-millisecond IPC read
coalesce into one React render, so the loading state is real, is correct, and is
never painted. The probe now waits for the **outcome** — the dialog's own panel
in the DOM — and clicks again each frame until it is there. Recorded as DC-89,
including the second draft, because a cleverer precondition is the wrong answer
twice.

**And the frame it finally took had a defect in it (DC-90).** The wiring table's
middle column — a part's name, the one cell with no class of its own — rendered
in a shade that is no token in the system. It was Chromium's default BLACK, on
Noć's blue-black panel: `color: var(--nx-text)` lives on `.nx-app`, and the
twenty components that render through `createPortal(…, document.body)` are
siblings of `.nx-app` rather than descendants. Every dialog in the app has been
legible only because each panel's children name a colour themselves — an
unwritten rule that held until the first `<td>` that did not. `body` now sets
the colour, one line beside the `background` that is on `body` for the identical
reason and whose comment already argues it. Dan never showed it, because there
the browser's default and `--nx-text` are both near-black; the theme that would
have exposed it is the one a light-mode reviewer never opens.

Twenty-eight tests over the generator, one over the catalogue rule, two more
over the bus rule. `packages/core` 5 932 → 5 961. The sweep re-run reports 2 549
frames and **0 findings**.

### E3 — the bench learns electricity (2026-08-31)

Founder: *„Ok nastavi to za elektroniku sto si hteo."* ADR-085's third slice of
six. Until now the workbench could tell you a wire went to a pin that is not
there; it could not tell you the pin was 3.3 V and the wire came from a 5 V
rail. It can now, in thirteen kinds.

**It is two modules, not one, and that is the whole design.**
`electronics/nets.ts` derives the electrical model — union-find over every pin
of every placed part, producing nets that carry which supply rails they touch
and whether they reach ground. `electronics/rules.ts` reads that model and
returns findings. ADR-085 §2 already said E3 comes before E4 and E5 because all
three consume the same derived fact — which pin carries what, at what voltage,
on which bus — and a sketch generator that re-derives it becomes a second rules
engine that will disagree with the first. So `buildNets` is exported from
`@nexus/core` alongside `circuitRules`, and E4 will consume it rather than walk
the wire table again.

**The thirteen codes.** `supply-unreached`, `ground-unreached`, `supply-range`,
`rail-conflict`, `rail-short`, `logic-level`, `output-conflict`, `bus-role`,
`i2c-address`, `current-budget`, `pin-capability`, `analog-signal`,
`led-unprotected`. Each finding carries a code, a severity, the parts it
involves and typed values (volts, milliamps, a range, an I²C address), so the
renderer formats numbers with the app's own helpers and the strings table stays
static — no interpolation, which is how every other strings table in the app
works and how `check:address` can keep reading them.

**Four judgement calls, all of them about false positives.** A rules panel that
fires on correct work is one the user stops reading, so each of these chose
silence over a defensible complaint:

- **Boards are exempt from the supply and ground presence rules.** An UNO has a
  `VIN` pin and is powered over USB in nearly every correct circuit. Demanding a
  wired supply would be wrong more often than right.
- **A peripheral's logic domain comes from the rail it turned out to be on**,
  never from its own catalogue entry. A 3.3 V sensor on a 5 V rail is a
  `supply-range` finding once; it must not also become a `logic-level` finding
  on every one of its signal pins.
- **A pin that commits to no bus role is never judged.** The ESP32 remaps I²C at
  will, and software I²C on ordinary GPIO is normal practice.
- **`current-budget` sums `typical`, not `peak`.** Summing every part's worst
  case would report a fault on almost every correct circuit. `boards.ts` already
  described `current.peak` as the number a budget works against; this is the
  narrower reading, and the honest one for a static engine.

`i2c-address` is the one rule with two severities: an `error` when neither
device can be strapped elsewhere, a `warning` when one of them can.

**The defect this pass produced, and how it was caught — [DC-87](../defect-classes.md).**
`led-unprotected` first asked whether a part with `valueUnit: "ohm"` was
anywhere on the anode's net. That is membership, and the property meant is
position: a resistor with one leg on that net and the other in the air protects
nothing, and a resistor on the *cathode* side protects perfectly and would have
been reported as a fault. The rule is purely topological now — driving pin
directly on the anode's net, ground directly on the cathode's net, nothing in
between — which deleted the `valueUnit` coupling entirely. It was found by a
**mutation test**: the demo circuits are correct, so „the engine returned
nothing" and „the engine is broken" look identical on them; taking the resistor
out of a demo circuit and asserting the rule fires is the only check that
distinguishes them.

**Two gates earned their keep on the way.** `check:invisibles` caught a literal
NUL byte in `nets.ts` — the node key had been `partId + NUL + pinId`, chosen
because no id can contain NUL. The fix was not to escape it but to stop needing
it: the key is length-prefixed (`${partId.length}:${partId}${pinId}`), which is
injective for any two ids and rests on no assumption about the alphabet.
`check:tokens` caught `--nx-letter-spacing-wide` in the new inspector CSS, a
name that does not exist; the real token is `--nx-font-tracking-label`, and
CSS would have dropped the undefined property in silence.

The severity chip in the panel is typographic and coloured only at the top of
the scale. There is deliberately no amber tier: orange is a banned system hue,
so a middle colour would be a colour invented for one panel and meaning nothing
anywhere else in the app.

**Three more findings came out of reading the finished code rather than
running it**, and all three are the same shape — a rule reached more than once
saying the same thing more than once. `rules.ts` indexed pins on
`partId + " " + pinId`, the very construct `nets.ts` had just stopped using;
it is a nested map now, which needs no argument about what an id can contain.
Every rule walks NETS, so one pair of parts joined by two wires produced two
identical findings and an RGB LED with three driven anodes produced three — the
engine deduplicates whole findings once, rather than seven rules each guarding
themselves. And the panel keyed its rows on code-plus-parts, which two findings
differing only in their FIGURES would have shared.

**The sweep, twice.** `shots` reported three text overlaps on the electronics
canvas at one size in one theme; a second run over the same commit reported
none, and the two runs disagreed on the frame count (2 538 against 2 537), so
that was the harness and not the module. What DID reproduce is the calendar's
2px week-grid clip, which §4 has carried as a known design question since
2026-08-21. The `Provere` panel photographs correctly and says „Nema primedbi
na ovo kolo" on both demo circuits, which is the engine staying silent in the
real renderer rather than only in a test.

Core 5 897 → 5 932 tests, desktop 1 952 → 1 954. Typecheck 13/13, lint 13/13,
build 4/4, `SMOKE OK`, all fifteen static gates green.

### Two dependency groups, one type that had been arriving, and 1.2.0 (2026-08-31)

Founder's order, verbatim: *„Baci push, proveri testove CICD, PRove sve to sredi
da bude kako treba, povuci izmene na local ako postoje i sve, i onda tek exe."*
Both open Dependabot pull requests are merged, CI is green on `main`, no pull
request is open, and the installer was built last.

**#27 (vitest 3.2.6 → 4.1.11) failed `pnpm typecheck` with 32 errors in 13 files
the bump does not touch** — and that, not the version number, is what the wave
was actually about. Root-caused by measurement rather than by guessing:
`tsc --listFiles` plus a lockfile diff. **tsc loads every `@types/*` package it
can reach by walking `node_modules` upward from each source file, and under pnpm
that walk goes *through* each declared devDependency's symlink into the store.**
Vitest 3 shipped `@types/chai` and `@types/debug`; that put an `@types`
directory on the walk, and all of `@types/node` came with it. Vitest 4 dropped
both, and thirteen packages lost `process`, `Buffer`, `TextEncoder`, `crypto`
and `URL` at once — names none of them had ever asked for. Recorded as **DC-85:
a type that ARRIVED rather than being declared**. The fix is six `tsconfig.json`
files that now say `lib` and `types` out loud, each with the reason written
beside it, plus `@types/node` as a real devDependency of the two packages whose
tests use it.

A first attempt — `"types": []` in `tsconfig.base.json` — **passed 13/13 while
still on vitest 3, which is precisely what proved it fixed nothing**: node types
arrive through `node:` module resolution, not through automatic inclusion. It
was reverted rather than shipped with a comment claiming a prevention it does
not provide.

Declaring `lib: DOM` then surfaced the finding worth having. `@nexus/sync-port`'s
real WebCrypto port carried a local `view()` helper for TypeScript 5.7's
`Uint8Array<ArrayBufferLike>` meeting WebCrypto's `BufferSource`; the **fake**
`CryptoPort` in `@nexus/sync-crypto` carried nothing — not because it was exempt
but because it compiled without `lib: DOM` and met Node's looser types instead.
**Two implementations of one port were being held to two different contracts,
and every sync test in the repository runs against the weaker one.** `view` is
now `asBufferSource` in `@nexus/sync-crypto`, exported from the barrel and
adopted at nineteen call sites, with the comment that matters attached to it:
handing `.buffer` to WebCrypto passes the WHOLE backing buffer and silently
authenticates or encrypts bytes the caller never offered, so the view is what
goes. `@nexus/core` keeps a deliberate second copy rather than growing a
dependency edge on the sync stack for a one-line cast, and says so in the file.

**#28 (the minor-and-patch group, 15 updates) was merged, not rebased-and-pushed.**
The rebase that verified it had rewritten Dependabot's commit, so landing the
branch would have needed a force-push; merging the original commit into `main`
instead made its SHA an ancestor, which is what closes a pull request as merged.
The merge's index was checked byte-for-byte against the verified tree before it
was committed. `@noble/ciphers 2.4.0` was not accepted on „31 tests passed" —
the two `draft-irtf-cfrg-xchacha-03` §A.3.1 vector tests were re-run explicitly,
because those are the ones that say sealed bytes are byte-identical.

**1.2.0 was cut** (`f3e6233`). Not bookkeeping: twenty commits sat on top of
1.1.0, four of them features, and a rebuild under the old number would have
produced an identically-named file reporting an identical `app.getVersion()` —
the ambiguity behind „I installed it and the module isn't there". The Gentoo

Gates at `f3e6233`: typecheck 13/13, lint 13/13, `pnpm test` green with **every
per-package count identical to the recorded baseline** — checked one by one,
because a green run can also mean nothing was collected — build 4/4, all fifteen

2 234/2 234, licences regenerated twice with **zero licence-term lines changed**.

**Tail: a red CI job that was not a defect, and the defect beside it**
(`04ba8ca`). The `database` job went red on `f3e6233` — `error running
container: exit 125` during `supabase db reset`, before any project SQL ran —
and passed on a re-run of the identical commit. Environmental. But the workflow
opens with a paragraph on why every `uses:` here is SHA-pinned (tags are mutable;

because one was wanted.

### The desktop can sync, and the build could not have run it (2026-08-30, W3.1)

Everything `syncOnce` needs had existed since 2026-08-17 and **nothing
constructed any of it.** Each piece takes its dependencies as parameters —
deliberately, so a browser tab can satisfy the same interfaces and a desktop
with cloud off holds nothing that could reach a network — which is exactly what
makes the absence of a caller invisible from inside every one of them. Three
files are that caller.

**`main/sync/round.ts` — the order of the refusals is the design.** A round
refuses in a fixed sequence: no ports, no account, locked, no token, no key.
The first three cost nothing and rule out a machine that cannot participate
whatever the server says; doing them AFTER the access-token refresh would spend
a refresh on behalf of a device that was never going to send anything — and a
refresh spends the STORED refresh token, so the cost is not a request, it is the
next launch needing a password. That is also what `session.ts` grew
`accessTokenForRound` for, from the other side: `freshAccessToken` had no
production caller at all (the same shape as DC-62), and its first one is a loop,
which is the first caller with no user behind it and therefore the first that
has to write the rotated token back. A FAILED refresh writes nothing, on
purpose: a 502 must not cost somebody their password.

Nothing in the file throws at its caller. Every refusal is a name, because the
caller's whole job is to tell „later" from „stop" and a stack trace says
neither — while the English `detail` strings the transport produces stay in
this process, as developer fault reports rather than user copy.

**`ContentKeySet.close` was renamed `zeroize`, and the rename is the fix.**
`check:zeroize` recognises a key release by the substring `zeroize(` —
narrowly, because `close(` is what a database, a file and a socket are released
with, and a gate that fired on all of them is a gate somebody switches off. So a
key set released as `keys.close()` sat exactly outside the reach of the rule
written for it (DC-61). Renamed, every present and future call site is inside it.

**`main/sync/scheduler.ts` — three destinations, not two.** `SyncHalt` has four
members because the engine's failures need four answers; a desktop round can
fail in ways the engine never sees (cloud off, database locked, no key on this
machine), and collapsing those into the engine's vocabulary would tell somebody
with a perfectly good session to sign in again. So the mapping is explicit and
exhaustive: **delay** (`offline`, `malformed`, `contested`, `locked` — locked
belongs here because it costs nothing, the round refuses before the first
request and the round after the unlock simply works), **halt** (`forbidden`,
`signed_out`) and **stop entirely** (`cloud_off`, `not_enabled`,
`key_unavailable`).

The scheduler also holds the nonce alarm across a profile switch, which is the
one thing in it that had to be got right. `createSyncLoop` latches on
`nonce-reuse` and nothing clears it — under XChaCha20-Poly1305 a repeated nonce
publishes the plaintext XOR and the Poly1305 forging key — but that latch lives
inside ONE loop object, and this file creates loop objects. A profile switched
away from and back to would have received a brand-new loop with a clean latch:
the latch bypassed by the only code that could bypass it. The scheduler
therefore remembers which profiles have poisoned, checked in `loopFor`, the one
place a loop is ever constructed, for the same reason the engine's check sits in
`arm`. Two mutations prove it: removing the check reddens two tests, and merely
MOVING the record after the staleness guard reddens exactly one — the round that
lands after a profile switch.

That staleness guard is the other rule. A round that finishes after the user has
changed profiles describes the profile it was STARTED for; recording its outcome
would file one profile's failure under another's name and stop a loop that is
not the one that ran.

**The contract is declared once.** `SyncActivityView` and `SyncProblem` live in
`shared/ipc.ts`, and `main/sync/round.ts`'s `SyncRoundBlock` is DERIVED from the
latter (`Exclude<SyncProblem, "nonce_reuse">` — that one is not a refusal to run
a round, it is what a round that RAN came back and said). The renderer's Serbian
sentence table is `satisfies Record<SyncProblem, string>`, so a refusal the core
grows and the copy does not name fails the build rather than reaching a user as
an empty line.

**Two defects found on the way, and neither was in the thing being built.**

*DC-83* — `check:zeroize` went red on `round.ts:39`, a line inside the file's
own header explaining the trap. The gate reads text and prose about a construct
is textually identical to the construct. This was the THIRD gate to meet it:
`scripts/strip-comments.mjs` was written for `check:egress`, adopted by
`check:elec`, and its header already says out loud that *„a gate firing on prose
about itself teaches people to stop writing the prose"* — and `check:zeroize`
was written afterwards without it. It is the worst instance of the three,
because for this gate the prose IS the countermeasure: the failure produces
plausible ciphertext and an error message that accuses the server, so every file
that meets it is supposed to write the wrong shape down.

*DC-84, and the bigger one* — `pnpm typecheck`, `pnpm lint`, `pnpm test` and
`pnpm build` were ALL GREEN on a build that could not start. `electron.vite.config.ts`
externalises node modules and bundles workspace packages, because those are
consumed as raw TypeScript; which packages are „ours" was a hand-written array
of eight names, and `@nexus/sync-engine` was the ninth dependency. Four of the

### The workbench, and the five defects that were not the feature (2026-08-21, `8fa6b25` … `4e20e26`)

„Elektronika" is the eleventh module and ADR-085's slice E2: a drawer of 153
components, a bench you place them on and run jumpers between, and a panel that
says what is selected and what is wrong with the circuit. Thirteen commits, of
which **four are the feature and five are defects met on the way** — which is
roughly the ratio the founder's clean-slate directive predicts, and the reason
the directive exists.

**The feature, in the four decisions that shaped it.**

The document is held in memory and **patched by each write's answer**. Every
mutation returns the row it wrote and the page applies exactly that, never a
re-read: on a board with forty parts, moving one would redraw everything. `patch`
refuses an answer whose circuit is no longer the open one — a write that lands
after a switch belongs to a document the page no longer holds.

Wiring is two clicks and **the first one is a mode**. A pin is armed, the hint
line says so, Esc disarms. The colour is chosen *before* the two clicks, which is
why the swatches sit on the bench bar and not in the panel; the panel recolours a
wire that already exists.

The geometry is a **drawing decision** and lives with the drawing.
`elecGeometry.ts` holds the bench's whole arithmetic with no React in it — part
sizing, the DIP pin order (down the left, back *up* the right), the one rotation
table both the pin maths and the SVG transform are derived from, and the cubic
that makes a jumper hang. It is not in `@nexus/core` because core owns facts
about hardware and this is one way of putting them on a screen. The single table
is load-bearing: a wire drawn to a pin the eye sees somewhere else is the one bug
on this surface a user could not diagnose, and `elecGeometry.test.ts` re-applies
the SVG transform by hand at all four angles and compares it against what
`pinPoint` computes.

The **catalogue is imported, not fetched** — a constant in core, no channel, no
table, nothing of it in an archive. A part carries a `componentId` the store
deliberately never resolves, so a component this build does not ship is drawn as
a dashed placeholder and *named* in the margin rather than refused. The circuit
is the user's work; a catalogue that shrank between two versions is ours.

**Defect 1 — a full export was silently leaving a whole module out.** Settings'
„Šta se izvozi" list was a hand-typed copy of `ARCHIVE_MODULE_IDS`, and it had
already drifted: ELEC made the interchange eleven modules and the copy still held
ten. `runExport` reads *that* array, so a user asking for a complete archive got
one with every circuit missing and nothing said so. There is nothing to notice —
a list that is merely **short** is a perfectly valid list, no type is violated,
the export succeeds. Same shape as DC-56's committed notices and DC-46's restated
default: a second declaration of a fact whose first declaration is the only one
that moves. The list is now the vocabulary itself.

**Defect 2 — the archive reader let an unbounded id through.** `idProblems`
bounded nothing: it asked only for a non-blank string, so a ten-megabyte `pinId`
was a legal wire. `RestoreStore` writes with prepared statements rather than
through `validatePart`, and the column's only CHECK is non-emptiness — so it
restored cleanly and produced a row no screen could show. Bounded in the model
(`MAX_ELEC_ID_LENGTH`) and again in the reader (`elecId`), on every id in all
three collections. The same pass renamed `MAX_CANVAS_COORDINATE` to
`MAX_PART_COORDINATE`, a misnomer in a module that is not the canvas.

**Defect 3 — a responsive fallback that reflowed along the wrong axis (DC-67).**
Below 1180px the drawer and the panel dropped *under* the bench. Arithmetically
correct, and it left the bench about a hundred pixels tall at the 900px minimum,
where the demo circuit framed itself at **20 %** — a photograph of a board rather
than a board. Height is the scarce dimension here: `fitView` fits both axes and
therefore takes the smaller ratio, so every pixel of instrument height the panel
takes is a proportional cut in the zoom. Stacked on the *rail* instead, the bench
keeps the instrument's full height: 435 × 600 where it was 105 × 600, and the fit
reads 66 % at the minimum window and 120 % wide. **The zoom figure was the
instrument** — it reports the layout's real geometry in one number.

**Defect 4 — a chart's axis was the data's range, not the ticks' (DC-69).** FIN's
balance flow printed „80.000,00" and „75.000,00" as one smear. Two functions,
neither wrong alone: `niceTicks` rounds both ends *outward* so the axis contains
the data, and `SeriesPlot` scaled the plot to the data's own extent — so the
first and last tick fell outside the drawing, where `clampTickLabelY` pinned them
to the edges and onto their neighbours. The clamp's comment and its test both
said it could only move a label three pixels; that was true of a tick already
inside the box, and **nothing stated the invariant that every tick would be**.
Worked by hand the displacement is 8.65px, and the sweep had measured 8.6 —
which is what confirmed the mechanism rather than merely fitting it. `tickDomain`
makes the ladder authoritative and the clamp goes back to being what it says.

**Defect 5 — two sweeps died, and it was one cause.** The screenshot harness
failed at ~2200 frames (`VizSentEmptyBitmap`) and then hung at 1215 frames with
four Electron processes at flat CPU and `Responding: True`. Both are Chromium
standing a window down when nobody is looking at it: `requestAnimationFrame` is
suspended in an occluded window and the compositor stops handing over frames.
**A measurement instrument that only works on an idle machine is an instrument
that reports on the machine.** Fixed at the cause (`backgroundThrottling: false`
plus two `--shots`-guarded switches; the webPreference alone reaches only the
renderer half) and at the symptom — `capture` retries four times and counts an
*empty image with no error* as a failed attempt, and every renderer call now
races a main-process timer.

That timer is DC-68, and it is the more general finding: `waitFor`'s
`while (Date.now() < deadline)` is unbounded, because **the deadline is only
consulted once the previous call has returned**. One `executeJavaScript` that

for every failure except the one it looks like it is there for. The ceiling went

**The audit itself was wrong about the workbench (DC-70).** With the sweep

exactly half `PIN_PITCH`, so the circles are tangent and any bigger one steals

later at 29px — one design, two verdicts, and the audit was reporting the zoom.

an exemption blinds the rule, a change of unit keeps it armed, and a genuinely
15px control inside the canvas still fails. Nothing outside an SVG has such a
chain, so every other surface is measured exactly as before.

**The fourteenth gate.** DEV-006 lets the workbench carry blue and orange, and
that scope was a sentence in `deviations.md` — a thing to remember. `check:elec`
makes it a rule: a `--nx-elec-*` token may be read or declared only in

stripper to blank `--` to end of line — would have blanked every custom-property
declaration in every stylesheet the *other* gates read. Narrowing the match to

### The content key, and an afternoon lost to the word `await` (2026-08-17, `3f5f65b` + `100b898`)

The subsystem the previous entry found missing is built. `openContentKey` opens
MK from this computer's wrap under DK, reads every generation of the profile's
content key, mints the first if the slot is empty, adopts the winner if another
device got there first, and hands back a `keyFor` map that answers for retired
epochs as well as the live one.

**One rule, made structural rather than remembered.** Never seal a row under a
key whose wrap is not already durable on the server: a row sealed under a key no
peer can fetch is a row no peer can ever open, and no later repair can invent the
key. That could have been a comment. Instead there is exactly one path in the
file that produces a usable key — `unwrapKey` over a wrap the server served. The
mint generates 32 bytes, wraps them, **erases the plaintext before the request
goes out**, and opens the row that came back. There is no branch where the two
could differ, so nobody has to remember the rule to keep it.

That erasure is also the one claim in the module a test cannot see from outside:
the plaintext is a local that never reaches the result, and the returned key is
byte-identical whether the mint kept it or not. It is proved by watching the
randomness it came from — a port wrapper that records every 32-byte draw, and an
assertion that the recorded array is zeroed by the time the call returns. Killing
the `finally` reddens that test and nothing else, which is what „uniquely
covered" means.

**`minted` reports the outcome, not the attempt.** A device that generated a key
and lost the race returns `minted: false`. Reporting the attempt would tell the
caller this profile joined sync on this machine, which it did not — and the
screen that will eventually read it is the one that says whether the account's
history starts here.

**A generation that will not open is reported, not dropped.** `unopenable`
carries the epochs this device cannot read; rows at those epochs quarantine,
which is the designed answer, but „generation 1 did not open" has to be
loggable. The same condition on the LIVE generation is fatal instead — there
would be nothing to seal under, and proceeding means pushing rows nothing can
read.

**And then the afternoon.** Three tests failed with a commitment mismatch, whose
message is „wrong password, recovery code, account or profile" — so it reads as
the server serving another account's row. It was data-dependent: generation 1
opened and generation 2 did not, which reads as one bad row. It was neither. The
call was

```ts
try {
  return openAll(deps, input, masterKey, wraps, false);   // async
} finally {
  zeroize(masterKey);
}
```

and a `finally` runs **at the return statement**, not when the returned promise
settles. The account's master key was erased in the middle of the very call that
was using it; generation 1 survived because its subkeys were derived before the
first `await` yielded, and generation 2 was decrypted under 32 zero bytes. The
fix is the word `await`, which is exactly the edit a reviewer deletes as
redundant.

The `finally` is not wrong — it is there so „MK lives as long as this call" stays
true when the call FAILS, which is a shape `service.ts` learned the hard way. It
was doing the right thing at the wrong time, and that is what makes this a class
(**DC-63**) rather than a typo. Blast radius: nine `try/finally` sites in the
repository return a call; the other eight return a value that is already
computed, so this was the only one.

**The thirteenth gate, `check:zeroize`,** triggers on `zeroize` and on nothing
else, and the narrowness is the design. A handle closed early throws `EBADF` on
the next call; a document destroyed early is gone. Key material erased early
produces plausible ciphertext and blames something else — it is the silent half
of the class, and a gate that reported eight correct sites for one real one is a
gate somebody switches off. `@typescript-eslint/return-await` states the rule
exactly for every type and needs type-aware linting, which `eslint.config.mjs`
deliberately does not wire; when that arc happens it replaces the file.

Two smaller things fell out of the gate rather than out of the feature. Its first
regex asked whether the returned LINE contained a call and reported three correct
sites — a value built from a call is finished by the time `return` runs, so the
rule is about the return's own expression. Its second version anchored on the
start of a line and missed `if (…) return openAll(…)`, which is one of the two
real sites. Both were caught by fixtures, which is the argument for a gate whose
rule can be exercised without the repository.

### The scheduler, and the key nobody had minted (2026-08-17, `8697a75` + `6b4fd25`)

The round existed and nothing called it. This is the entry for the half of that
which is now finished, and for what the other half ran into.

**The scheduler is not a `setInterval`, and `SyncHalt` is why.** A round returns
one of four halts and they need four different answers, which is the only reason
this is a module rather than three lines in the desktop. `offline` and
`malformed` are delays — backed off with equal jitter, to a ceiling that is
deliberately the idle interval itself, so the worst case of failing is the
ordinary case of being idle. `malformed` being a delay is the one that looks
wrong and is not: a page this build cannot parse leaves the PUSH half of a round
untouched, and a device that stopped syncing over somebody else's bad row would
be holding the user's own writes hostage. `forbidden` is not a delay at all, and
a timer there is the actual defect it prevents: a revoked session is not fixed by
waiting, so a backoff turns „sign in again" into an app that quietly never syncs.

**`nonce-reuse` latches, and it took a mutation to get that right.** The first
version checked the alarm in `start`, in `nudge` and in `syncNow` — three checks
that all had to stay correct. Killing the one in `nudge` left the suite green,
because poisoning also clears `wanted` and `nudge` refuses on that instead; the
check was unreachable defence rather than a rule. The fix was not to write a test
for it but to move it: `arm` is the one place a round can be scheduled from, so
the refusal lives there and every present and future caller inherits it. Arming
also became the act of leaving a halt — which is why `stop` may not clear the
reason, and why that got its own test after the same sweep found it unguarded.

**The interval is a deadline, not a gap — found by a red test, not by design.**
Two tests failed on the first implementation because a nudge pulled the wake
forward and the round after it re-armed a fresh interval from there. Follow that
through: a user typing steadily keeps producing hinted rounds, each one re-arming
the interval, and the full walk that exists precisely to catch what the hints
missed never runs at all. Measuring from the last COMPLETED full round fixes it
without any special case — coverage is decided when a round starts, from how long
it has been. „Completed" is load-bearing: a round that halted stopped somewhere
in the middle of the collection list, and counting it would push the next
complete walk an interval into the future on the strength of a walk that did not
happen. Nine mutations, all killed; three of the nine were rules that had no test
until the sweep asked.

**Then the wiring, and what it hit.** The desktop half needs `contentKey`,
`ckEpoch` and `keyFor` before it can construct a single round — and no profile
has a content key, no `key_wraps` row of kind `ck_under_mk` has ever existed, and
`generateContentKey` is called by tests and by nothing else. Everything around it
is finished to a high standard: the column, the epoch in the AAD, the argument
for why the epoch has to be there, the slot uniqueness, the wrap helpers. The
subsystem in the middle was never built, and nothing said so because every part
of it that WAS built is correct.

The wire half went in with the finding. Three of its rules are worth keeping:
the read does not filter `disabled_at`, because a retired generation is still the
only key that opens rows sealed under it; one bad row fails the whole response,
because a partial read here is indistinguishable from „this profile has no
content key" and the answer to that is to mint a second one; and the mint adopts
what the server returned rather than what it sent, because those are two
different claims and only one is evidence.

It carries three base64url strings rather than a `SealedKey`, and that absence is
the interesting part. `wrap.ts` is missing from `@nexus/sync-crypto/web` in its
entirety so a browser is never one `unwrapKey` from the master key, and
`web-key-surface` enforces it by walking `@nexus/web`'s dependency closure — a
closure that does not contain `@nexus/sync-transport` today and will the day the
web app syncs. So the obvious import would not have been a mistake that gets
caught; it would have been one planted now to fire months later, in a gate whose
message names a different package. The general shape: **a gate that checks a
closure only forbids what is in the closure today, and „not yet in scope" is not
the same as „allowed".**

**And a decision that only exists in the docs.** Minting is a client INSERT, not
an Edge Function, because the server has never held MK and cannot wrap what it
must never see — a function would be a proxy for the same insert with no extra
authority, and `key_wraps_one_per_slot` is a better arbiter of „exactly once per
slot" than application code, because two desktops minting in the same second
cannot both win. Nothing blocks it on the server.

**A finding that was not one, which is the part of this entry worth reading.**
This work was reported as blocked on a missing privilege: `authenticated` has no
`insert` on `key_wraps`, so `key_wraps_owner_insert` is a dead policy and the
mint needs a change to the security wall — escalated to the founder, with a
migration drafted and a defect class written. It is false. The grant is forty
lines above the policy in the same file, column-scoped, and it names all seven
columns a `ck_under_mk` mint writes. The evidence was `grep`, and the statement
puts its verb on one line and its table on the next.

The miss is ordinary. What it cost is the class (**DC-62**): every step after
the premise was sound — the migration, the confining policy, the ledger entry,
the request for authorisation — and derivation preserves falsehood exactly as
faithfully as truth, so the work built on top read as evidence for the thing
that started it. Meanwhile `check:rls`, which parses statements rather than
lines, had been reporting the wall sound at every gate run; that silence was
read as „not a rule it checks". **When a hand-search and a parser disagree about
the same file, the parser is right.**

The shape that was wrongly reported is real, so it became rule 8f of
`check-rls-wall.mjs` rather than a note: grant and policy are two gates in
series, the privilege answers first with `42501`, and a policy on a privilege
its role lacks never runs; the mirror image — a write grant no permissive policy
admits — is a statement that touches zero rows and returns HTTP 200 `[]`. Both
directions are asserted per privilege, and `clientGrantsOf` now replays REVOKEs,
so what the gate reads is the state the migrations END in rather than the widest
state they ever had. Three mutation tests, each proving one half can fail. Had
the grant genuinely been missing, one command would have said so — which is the
only useful outcome available once the finding turned out to be about a grep.

### The loop, and the first row to cross between two machines (2026-08-16/17, `29e6493` + `e85e283`)

Four packages existed and nothing put them together. This is the entry for the
two commits that did: the derivation a push had been missing, and the round.

**`parentIdOf`, and the trap that makes it not a one-liner.** A pushed row names
its parent so the server's RLS wall can check the row belongs to the profile the
session claims, and until now nothing computed it. The obvious implementation is
`state.fields[collection.profileVia.key]`, and it is wrong for two of the eight
parented collections. `fieldColumns` **subtracts the identity columns** from the
field map, and `note_versions` and `note_updates` are identified by
`(note_id, …)` — so their parent key is not a field of the state and never will
be. The derivation therefore asks where the key IS before asking what it is: in
the identity, take it out of the object id; otherwise read the state. The failure
it avoids is quiet — a null `parent_id` on a row the wall would then refuse, on
two collections, for ever.

Two of that file's tests are not tests of the function at all but of its
**preconditions**: every `profileVia.parent` names a collection identified by a
single column, and every `profileVia.key` is a column the collection really
carries. Both are true today by construction and neither is checked anywhere
else; the derivation silently depends on both, so the map is where a future
addition would break it.

In the same pass the object-id encoding moved into `@nexus/sync`. It had been
written in three places — migration 063's SQL, `@nexus/db`, and `wire.ts`'s
length bound — and owned by none, which is the shape a defect copies itself
along. It belongs to the package that owns the wire, because the browser will
have to split an object id with no `@nexus/db` anywhere in sight. The constant is
`String.fromCharCode(0x1f)` rather than an escape sequence in a string literal:
`check:invisibles` exists because a character that renders as nothing is one a
reviewer cannot see, and the rule does not stop applying inside the file that
defines it — least of all there. Migration
063 keeps its literal `char(31)` — its triggers are already in every user's file
and rewriting SQL that has run is not a refactor.

**The round is sweep → pull → push, and each arrow is a rule.** Sweep first,
because the write-back refuses an object whose local edit is still in the
journal — pulling first would produce `stale` for exactly the objects the user
just touched. Pull before push, because `owed()` reads the shadow state through a
JOIN: an object owed before the pull is automatically owed at its MERGED state
afterwards, without the engine arranging anything. Reverse those two and the same
work becomes a stale push, an NX001, and a second round. Nothing retries inside a
round — how long to wait is a scheduler's question with a platform's answer, and
everything that must survive is in tables.

`@nexus/sync-engine` holds no `fetch`, no database and no clock; all three arrive
in `SyncDeps`. That is what makes cloud-off structural here rather than
configured: a desktop that never constructs the ports has nothing in this package
that could go looking for one.

**The deadlock the two watermarks exist to avoid.** A pull walk carries two
numbers: where the next PAGE starts, and what is written to `sync_cursor`. The
temptation is one number, and it deadlocks. A child that arrives before its
parent is refused by a foreign key, and its parent is very often further down the
same log — so holding the walk back at the refusal leaves the parent in a page
nobody fetches and the child refused for ever, on a log that already contains its
cure. The walk carries on and writes the parent; the cursor stays behind the
child so the next round is served it again. The hold latches for the rest of the
walk and across its pages: „the last CONSECUTIVE success", not „the last
success", and a property of the walk rather than of a page — which matters
because `max_rows` truncates a page without saying so, so a page is „done" only
when it comes back EMPTY.

**A gap in `SyncJournal.apply` that only the loop could reveal.** `applyPull`
answers `owed: true` when a merge differs from what the server holds — a local
edit the peer had not seen, folded into an arriving row — and that fact lived
only in a return value. The apply runs with migration 063's trigger flag off, so
it journals nothing; and afterwards the row and the shadow state agree, so no
sweep can rediscover it. The edit would be on this device, correct, and never
sent again. `ApplyRequest.owed` is now REQUIRED and queued inside the row's own
transaction — the same defect and the same fix as the sweep's outbox, in the
other direction, which is what makes it a class and not a bug.

**Running it corrected the report** (DC-60). `applied` counted every write-back,
so with `PULL_OVERLAP = 64` a fully caught-up device reported work on every round
for ever; it now counts only the merges that CHANGED the local tables. And `owed`
was `owed(1).length` — documented as a count, capable only of 0 or 1, and it is
the number a screen shows. The port gained `owedCount()`, answered by a `count(*)`
over the same JOIN `owed` uses, so it cannot report work the push can never find.

`SyncStore` is declared by the engine rather than by `@nexus/db`, because the
consumer names what it needs and a browser tab has no SQLite. `@nexus/db`
satisfies it through `syncStoreFor`, which binds the profile — a port that took a
profile id per call would let a round write another profile's rows, and closing
over it makes that unrepresentable rather than forbidden. The port also states
what the engine quietly relied on: `apply` returns ONE OUTCOME PER REQUEST, IN
ORDER, because the cursor arithmetic pairs them by position. A store that answers
short is treated as a hold rather than trusted.

**`syncRound.test.ts` is the point of all of it**: two real SQLite databases and
one in-memory server, and a task created on one machine arriving on the other by
the mechanism that will actually carry it — plus a deletion, a two-device merge
of different fields of one object, and an object that stays owed across a round
that could not reach the server. It found two things a unit test could not. The
first was mine: both devices read the same wall clock, and since that string is
the HLC's physical component, every merge fell through to the node-id tie-break —
a coin flip, and a test decided by one is a test about nothing. The fix is a
shared, advanceable clock, which is also the honest model of two machines. The
second was the report, above. The harness now prints every round it saw when it
fails to settle, because „it did not settle" is equally true of a loop stuck

### „Programerske alatke" became „Stručne alatke": one drawer, eighteen toolkits (2026-08-13)

*„svidja mi se kako si odradio za programere. Sada hocu da osmislis tako za sve
profesije… neki alati mogu da se javljaju izmedju vise profesija ako je
prikladno."* And, once the shape was standing: *„za sve te oblasti Medicina,
treninge, zdravlje, pravo, gradjevina, sve to sto je jako zakonski regulisano,
da obavezno stoje vidljivi disclaimeri za sve."*

**The shipped model could not be scaled, and the reason is worth stating.**
Until this week a tool reached its drawer through its CATEGORY:
`TOOL_CATEGORY_DRAWER` mapped each of the eleven categories to exactly one of
two drawers, and the second drawer was a module called `devtools`. Generalising
that to twenty-two professions had exactly two readings, and both are wrong.
Register twenty-two modules and a person with one job gets twenty-three sidebar
rows. Keep one module and route by category, and a tool belongs to exactly one
profession — so the colour converter a designer and a programmer both live in
would have had to exist twice, which is the thing the founder explicitly asked
not to happen.

**What replaced it.** One professional module, `pro`, and a new field on the
registration: `packs?: readonly ToolPack[]`. Absent means everyday tool
(„Alatke"); present means professional („Stručne alatke"). Sharing is then a
longer array rather than a mechanism — `qr` is `["softver", "biznis", "event"]`
and appears once, in one place, for three trades. Inside the professional drawer
**packs filter and categories group**, so a photographer and an event planner
find the same tool under the same heading and neither is told it was also
somebody else's.

**A pack is a SUBJECT, not a job title, and that is the load-bearing decision.**
„Gradnja i projektovanje", not „Arhitekta". A job-title list fails closed on
every trade nobody thought of — a *geodeta* is not an architect, a
*tapetar* is not a joiner — and a list that fails closed on the user's own word
teaches them the product is not for them, on screen two. A subject fails open:
you recognise the work even when your title is not on anyone's list. The cost is
that a person scanning for themselves wants to see their own word, which is what
the second line of every card is for (`strings.pro.packs[…].who`).

**The questionnaire's „Uloga" screen is gone, and it was carrying two bits.**
Five buttons — student / zaposleni / preduzetnik / programer / drugo — of which
`zaposleni` and `preduzetnik` were byte-identical rows, and `student`, `drugo`
and „Osnovno" were the same row again. Scaling that to twenty-two job titles
would have scaled the ceremony and not the payload. It is now **„Šta se sve nađe
u tvojoj nedelji?"**: multi-select cards, one per stocked toolkit, uncapped,
with nothing signalling that one answer is normal and three are greedy — the
professor who also freelances is the ordinary case.

**The card table does not exist**, and that is the design rather than a
shortcut. `packInventory` walks the registry and offers one card per pack that
has at least one tool. So *„never offer a toolkit that is not built yet"* — the
founder's 2026-07-12 „only built modules are registered", one level down — is a
**property**, not a rule somebody has to remember: an empty pack is unofferable
because there is nothing to build a card out of. The old five-role table would
have become a twenty-by-thirteen matrix of 260 hand-maintained cells.

**Module inference is one line, on purpose.** `applyPackSelection` sets `pro`
and touches nothing else. The obvious design gives every card a module delta —
„Fotografija" turns „Učenje" off, because a photographer is not sitting an exam
— and that is a guess of the *wrong kind*: the card question asks what somebody's
WORK is about, and „Učenje" is a fact about their life. A caterer may well be
finishing a degree. The old screen could subtract honestly because it asked about
the person's status directly; this one does not ask, so it does not answer. What
IS derived is `pro` itself, because that is an identity and not a guess: every
tool in the drawer belongs to a pack, so turning the module on with the first
pack and off with the last makes „an empty professional drawer" *unreachable*
rather than merely unlikely.

**Where a toolkit is switched.** One component (`ProPacks.tsx`) in three rooms:
a dialog off the drawer's own header („Paketi…"), a card in „Podešavanja", and
the questionnaire's receipt on screen three. A checkbox list in Settings and a
card grid in the drawer would have been two answers to „what does a chosen
toolkit look like", and the questionnaire would have been a third.

**Migration 65** carries existing files across: `feature_flags` rows saying
`devtools` become `pro`, and each mints a `pack:softver` row *inheriting its own
value*. Inheriting matters — every business profile and every completed first run
stores explicit `false` rows, and a migration that answered „yes" on their behalf
would be this codebase's own „an unset field ships the toolchain's answer" defect
wearing a different hat. `ON CONFLICT DO NOTHING`, so a choice made *after* the
upgrade survives a re-run. Five cases pinned in `migrations.test.ts`.

**A pre-existing hole closed on the way (blast radius, not the sample).**
`flagsSet` accepted any non-empty string as a flag key, and `feature_flags` is a
generic key→boolean store with no constraint of its own — which is exactly what
made it the right home for packs and exactly why it needed a gate. `asFlagKey`
now closes the domain: a registered *unlocked* module id, or `pack:<id>` for a
known pack. Locked modules are refused too, since `dashboard` and `settings`
cannot be switched off anywhere in the UI, so a row for one is a stored fact no
surface can act on.

**Three dead things surfaced by the rename, each its own small defect.** The
drawer's density rules were keyed on `.tool--developer`, a class no element has
carried since the modifier became `professional` — so the whole density block
had silently stopped applying. `.onb__demo` was rendered with no rule anywhere,
which is the same failure in the other direction. And the demo profile enabled
every module but no pack, so `--demo` and the screenshot sweep would both have
opened the newest surface in the app onto an empty list — and the sweep would
have reported it as „found nothing to fan out", i.e. a false alarm about a drawer
that works. All three are one class: **a name that only one side of the app
knows**, and nothing currently gates it (see DC-37 in §5).

**Seven categories were added, and the seven are the price of the axis.** Eleven
were enough while the professional drawer was one trade's; across eighteen
toolkits `calculation` would have collected a hundred and fifty tools and stopped
being a heading — a group that contains everything sorts nothing. The new ones
are `geometry`, `materials`, `structure`, `electrical`, `media`, `body`,
`finance`, and they are still verbs rather than trades, which is what keeps the
doctrine intact: a bricklayer's lintel and a rigger's sling are both `structure`
because both ask what an assembly can carry, and neither pack owns the word.
There is deliberately no `legal` and no `land` — a limitation period is a date
(`time`), a court fee is money (`finance`), a parcel is a polygon (`geometry`).

**The disclaimers are a property of the contract, not copy — and they are
built.** `riskClass` is a REQUIRED field on every registration with `"none"`
spelled out, so omitting it is not expressible; it decides four things the tool
itself never gets to decide:

  1. **the notice above the body** (`ToolRiskNotice`), drawn by the HOST from the
     registration, so a tool cannot ship without one or ship with the wrong one.
     A `<details>` — one quiet line, the long form folded behind „Detaljnije". Not
     a warning box: an amber panel repeated across eighteen toolkits is banner
     blindness with a border, and it is the look the design rules ban anyway;
  2. **a line appended to every copied result** (`useCopySuffix`, read by the
     shared `CopyButton` through context, so no surface can forget it). This is
     the only one of the four that leaves the window — the harm nearly always
     happens downstream, in the email or the site diary, which is also the only
     place a third party ever meets the number;
  3. **the long form in „Podešavanja"**, listing *every* class including the ones
     this profile's toolkits do not reach, because „what does this app claim
     about regulated work" is asked BEFORE a toolkit is switched on;
  4. **`toolForbidsVerdict`** — for `life-safety` and `food-safety` the surface
     may not render a judgement at all. That one is not about text: „is a green
     tick allowed here" is not a question a surface should answer for itself.

Classes are told apart by the HARM and never by the trade, which is why a
rigger's sling load and an electrician's cable drop are one class. Every notice
says what the tool IS and none apologises for what it might do — enumerating a
harm proves it was foreseen, leading with a waiver reads as a product expecting
to hurt somebody, hedging the accuracy concedes the arithmetic may be defective,
and claiming compliance is a warranty. Two tests in `modules.test.ts` make the
omission fail loudly: the categories whose failures land on somebody else
(`structure`, `electrical`, `body`, `finance`) are refused a harmless class, and
a verdict is refused in the name of any tool not allowed to render one.

**Acknowledgement is the switch, not a modal.** The picker and the questionnaire
both carry `picker.responsibility` — one sentence saying the tools do not replace
the professional who is answerable for the decision. A consent dialog would be
dismissed unread by the second toolkit and would teach the user that this app's
warnings are furniture on the way to the tool.

**Constants have three tiers, and the middle one is the correction.** My first
rule was „no embedded constant any authority can revise", which Fable showed was
over-broad — it would have destroyed the rebar tables and the depth-of-field
circle of confusion along with the tax rates. The rule now: `physical` (g, π,
water density) embeds freely; `published` (ISO 216, EAN weights, ISO 286) embeds
**with its source and edition rendered under the answer** via `sourceKey` —
provenance, never a compliance claim; `regulated` (tax rates, statutory
deadlines, partial factors, cooking temperatures, axle limits) is **never
embedded and never defaulted** — the user types it and the tool echoes it beside
the result, because an embedded figure is the vendor asserting what the law
currently says.

**The `zdravstvo` pack was removed rather than shipped.** What makes software a
medical device is its INTENDED PURPOSE, and intended purpose is established by
what the product says it is for — so a `who` line reading „lekari, medicinske
sestre" is a clinical claim about everything in the pack that no disclaimer
retracts (*SNITEM*, C-329/16: software checking a dose against patient data is a
device though it never touches the patient). Fable found two such claims already
in the tree: that audience line, and the phrase „a doctor, a nurse, a dentist and
a vet want ONE set of body-mass and **dosing** arithmetic" in `TOOL_PACKS`'s own
comment. Both are struck. „fizioterapeuti" and „nutricionisti" came out of
`trening` and `kuhinja` for the same reason. The decision the founder still owns
is in §5.

desktop; all four LOCAL and unpushed): `pnpm typecheck` 12/12, `pnpm test` 11/11

### The seventeen toolkits, part 1 — the arithmetic (2026-08-13, committed)

**274 tools, in 17 modules under `packages/core/src/pro/`, ~43 000 lines of code
against ~36 600 lines of test — 1 991 assertions, every vector derived by hand
before the function existed.** Committed as `e977094` (the `gradnja` pilot,
end to end), `29ee1e4` (the other sixteen plus the shared kit) and `b90b991`
(the gate). All three are LOCAL and unpushed.

**Why the core is a separate layer at all.** These are the only tools in the app
whose *output* somebody acts on outside the window — a cable cross-section, a
sling angle, a limitation period. Splitting the arithmetic away from the screen
means the number can be tested without a DOM, and the screen has nothing left to
get wrong: the discipline every one of the seventeen files states at its head is
that **the surface shapes fields, hands numbers over, and reads answers back — it
does not divide, round or compare.**

**One shared kit, `pro/result.ts`, and it is the reason the 274 agree with each
other.** `ProResult<T>` is a discriminated union — `{ ok: true, … }` or a
`ProFailure` naming which field is at fault — so „the tool refused" is a value
and never an exception, a `NaN`, or a zero that reads like an answer. The guards
(`isPositive`, `isNonNegative`, `isInRange`, `isIntegerIn`, `isKeyOf`,
`isOneOf`) and the arithmetic (`quotient`, `snap`, `floorSnapped`, `ceilSnapped`,
`roundHalfUp`, `ratioAgainst`, `minorUnits`) exist so that a rule lives once. Two
of them are worth naming: `quotient` refuses a division by an unguarded input
rather than returning `Infinity`, and `roundHalfUp` exists because
`Math.round(-0.5)` is `-0` and half of the money in this drawer is negative.

**A tenth static gate, `check:pro-math`.** It reads all 17 core modules and all
17 surfaces and fails on three constructs: a private copy of a helper the kit
already has, an absolute epsilon on the same line as a rounding call, and a
division by an input nothing guarded. Its own test suite is 25 cases. It was
written after the modules, which is exactly why it had to be extended twice —
see DC-45.

### The two red CI jobs, and what each of them turned out to be about (2026-08-10)

*„Popravi CICD koji je pao."*

Two independent failures on the same push, neither of which was about the push.

---

**A. `Security / Secret scan (gitleaks)` — two reviewed non-secrets, and a gate
whose green meant less than anyone read into it.**

The two findings, both confirmed harmless by reading the code that produces
them, not by their looking innocent:

| Where | Rule | What it actually is |
| --- | --- | --- |
| `packages/core/src/devtools/cryptoTools.ts:1486` | `private-key` | A JSDoc naming the PEM armour of `PemKeyPair`'s two fields. The rule matches armour, not key material, so it opens on the `PRIVATE KEY` label and closes on the `PUBLIC KEY` one — a three-line match that is entirely comment. |
| `packages/core/src/priv/privEnvelope.test.ts:39` | `generic-api-key` | `BLOB_KEY_HEX`, the known-answer vector for `derivePrivBlobKey` — HKDF over `PRIV_DEK`, which the same file defines as `bytes(32, (i) => i)`: the bytes `00 01 … 1f`. It protects nothing and anyone can recompute it. |

**The subsystem finding, which is the part worth keeping.** `gitleaks-action`
picks its scan range from the event and offers no input to change it — read out
of the pinned action's own `dist/index.js`: `push` and `pull_request` scan
`base^..head`, only `schedule` scans the history. So a push-event green means
*„this push added nothing"*, while it is read as *„the repository is clean"*.
Those came apart in the most literal way available: **run `30624013396` failed
on 2026-07-31 on this exact fixture**, the next push went green because the
window had moved past that commit, and the finding then sat inside a green
repository for ten days until the first scheduled full scan reported it again.
Nothing was fixed in between; the failure was outlived.

The fix is therefore two things, not one. `.gitleaks.toml` records the two
reviewed literals, and `security.yml` now runs gitleaks directly — pinned by
version *and* by the release archive's SHA-256, which is strictly stronger than
the action, since the action downloaded a release at run time and verified
nothing — scanning the **whole history on every event**. About seven seconds for
this history, which is no reason to check less.

**The config's shape was measured, and measuring it is the whole story.** Every
allowlist mechanism the current documentation suggests is *silently inert* in
the pinned gitleaks 8.24.3: `[[allowlists]]` (plural), `targetRules` and
`matchCondition` are unknown keys, and TOML drops unknown keys without a word —
a config using them scans exactly as if it were absent, which is what the first
candidate did while looking correct. What works is the singular `[allowlist]`,
whose conditions **OR** rather than AND, so a `paths` entry does not narrow an
exemption to a rule: `paths = ['.*\.test\.ts']` would have quietly stopped the
scan from ever reporting an AWS key or a GitHub token in any test file. Proved
by planting both and watching them disappear. The entries therefore name the
literal itself.

**Proved in both directions, because a suppression is only as good as what it
still refuses.** With the config: the full 413-commit history scans clean. The
counter-test plants a real private-key body in the very file whose PEM label is
excused, and an AWS key, a GitHub PAT and a JWT beside the excused vector, plus
a *different* 64-hex constant on the next line of that same file — **all six
still fail**, and the two reviewed literals stay exempt. The file this change
adds scans clean under the stock ruleset too, so the fix cannot fail the next
run on itself.

**One byte was hiding a whole file from the scanner.** The blast-radius sweep
found `packages/core/src/devtools/jsonTypes.test.ts` carrying a raw `0x00` at
offset 2876 — a fuzz input written as a literal NUL rather than as the escape.
Git's binary heuristic looks at the first 8 000 bytes, so `git log -p` emits
„Binary files … differ" for it, and a history-scanning secret gate reads exactly
that patch: **the file has never been scanned, and never would have been.** A
secret committed there would have been invisible. Written as `"\x00"` the
runtime string is identical and the file is text again.

**And the escape alone does not fix it — a correction to what the first commit
of this change claimed, found by checking after committing rather than before.**
`git diff` marks a pair binary when *either* side is, so even the commit that
removes the byte has an opaque patch; and `gitleaks detect` reads commit patches,
so it only ever sees lines that were *added* in a scanned commit and never reads
a file whole. The gate therefore grew a second step: `--no-git` over the tree,
which reads files instead of patches. The two answer different questions —
*„was a secret ever committed"* and *„is one here now"* — and neither contains
the other. Proved: a fresh checkout is 1 017 files and 17.4 MB, scans clean in
445 ms, and a secret planted in the very file the history scan cannot see is
caught.

---

**B. `CI / verify` — `pnpm test` failed on a timeout that was not the code's.**

`packages/core/src/bytes.test.ts:38`, *„survives an input far past the
argument-count limit"*, took 6 802 ms against the 5 000 ms default. Measured
rather than assumed, which changed the answer: the codec is linear and fast —
300 000 bytes encode in **13.9 ms** and decode in **1.2 ms**, and the scaling
run from 37 500 to 600 000 bytes is flat per byte, so there is no quadratic bug
to find. **370 ms of the test's 390 ms was `toEqual`**, walking a 300 000-element
pair through vitest's structural equality at about 1.1 µs per element. The
assertion cost seventeen times what the behaviour under test cost. It now
compares lengths and then the index of the first differing byte: **19 ms**, and
a failure names the byte instead of printing 300 000 of them.

**And it was not alone, which is the finding.** The same run has
`RestoreStore > T10` **passing at 4 332 ms**, with six more between 3.4 s and
4.2 s — under a 5 s default that nobody in this repository ever chose. That is
668 ms of headroom on a shared runner whose speed is not ours to control, and
the next slow scheduling turns a different test red each time, which reads as
„flaky CI" rather than „something broke". `packages/db/vitest.config.ts` now

### Linux — an AppImage, a tarball and a real Gentoo ebuild, plus the description the Windows installer had been showing all along (2026-08-10)

*„kad budes napravio exe za windows, pls napravi i installer za Gentoo Linux ako
je moguce, ako nije onda samo windows."*

**It was possible, and „installer" is the wrong noun for Gentoo.** Gentoo has no
installer file: its unit of installation is an *ebuild* inside a *repository*
(an overlay), and for a prebuilt Electron app the correct shape is a `-bin`
ebuild that unpacks a release tarball into `/opt` — portage is not going to
rebuild Chromium from this tree. So one build now produces three things:

| Artifact | Size | For |
| --- | --- | --- |
| `Nexus-1.1.0-x86_64.AppImage` | 204 MB | Any glibc desktop, no packaging at all. `chmod +x`, double-click. |
| `nexus-1.1.0-linux-x64.tar.gz` | 205 MB | What the ebuild installs; also a fine manual unpack-and-run. |
| `app-office/nexus-bin/nexus-bin-1.1.0.ebuild` + overlay | — | The real Gentoo install: `emerge nexus-bin`, menu entry, icon, `/usr/bin/nexus`. |

The overlay lives in `apps/desktop/build/gentoo/` (`metadata/layout.conf`,
`profiles/`, the ebuild and its `metadata.xml`), with a README covering the
build, the AppImage, `repos.conf`, `ACCEPT_LICENSE`, the distfile and the
`Manifest`.

**The committed `Manifest` is a snapshot of one build, not a property of the
source** — it pins the size and BLAKE2B/SHA512 of the tarball that was actually
delivered, and any rebuild produces different hashes (neither tar nor gzip is
reproducible here), at which point portage correctly refuses the distfile. That
is inherent to a `-bin` ebuild and the README carries the one-line regeneration
command, but it stops being a manual step only when `SRC_URI` points at a real
GitHub release and the Manifest is cut from that published file. Recorded here so
the coupling is a known property rather than a surprise at the first rebuild.
The DC-33 fix below deliberately did **not** trigger a Linux rebuild: `author`
reaches Windows resources only, no Linux surface reads it, and rebuilding would
have invalidated the delivered pair to change an unread field inside an asar.

**Built on Linux, and only on Linux, on purpose.** `scripts/dist.mjs` now picks
its target from `process.platform` and refuses anything else. electron-builder
would happily emit a Linux target from Windows; the native module underneath us
would not, because `rebuild-native.mjs` fetches the prebuild for the host, so a
cross-built archive would carry a Windows `.node` and die at the first query with
an error about the module rather than about the build. WSL is enough — no
Docker, no VM — and that is where these artifacts were built and verified.

**Six things the Linux target forced into the open.**

1. **The window icon was Windows-only and nobody could have noticed.** The main
   process resolved `build/icon.ico` unconditionally. Chromium's ICO decoder is
   compiled in on Windows alone, so on Linux that is not a smaller icon, it is
   *no* icon, silently, with the toolkit default in its place.
   `build/make-icon.ps1` now emits a 512×512 `icon.png` from the same geometry
   and the same tokens, both files ship, and `index.ts` picks by platform.
2. **The Chromium sandbox stays ON in the AppImage.** electron-builder's default
   for the FUSE2 AppImage toolset is `--no-sandbox`, and that is a real
   downgrade for *this* app: the renderer displays documents and attachments the
   user supplied. `appImage.executableArgs: []` overrides it. The price is a
   host with unprivileged user namespaces disabled — there the AppImage refuses
   to start rather than starting unprotected, and the ebuild covers that case
   properly by installing the SUID sandbox helper at 4711.
3. **Window association was never configured.** Electron derives its Wayland/X11
   `app_id` from `desktopName` in `package.json`; without it, a running window
   does not attach to its launcher and shows up as a second, nameless dock icon.
   `desktopName` is now `rs.stojiljkovic.nexus.desktop`, equal to `appId`, with
   `linux.syncDesktopName: true` so electron-builder names the `.desktop` file
   and its `StartupWMClass` from the same string. Verified by extracting the
   AppImage and reading the generated entry.
4. **`RDEPEND` is measured, not copied.** Every atom in the ebuild is one
   `DT_NEEDED` entry of the shipped binary that glibc and gcc do not already
   provide, read with `readelf`. Two entries are there despite not being
   `DT_NEEDED` and are commented as such: `app-crypt/libsecret`, which Electron
   dlopens, and `x11-misc/xdg-utils`, which `shell.openExternal` execs. The list
   was then *tested*: installing exactly its Debian equivalents into a WSL image
   that had no desktop libraries at all was enough to make the app start, so the
   list is complete rather than plausible.
5. **The default AppImage cannot start on a current Linux desktop.**
   electron-builder's default toolset builds a FUSE2 image, which needs
   `libfuse.so.2` — a library Ubuntu 22.04+, Fedora 38+ and Gentoo stopped
   installing when they moved to FUSE 3. The first build died with
   `dlopen(): error loading libfuse.so.2` before a line of app code ran. Pinning
   `toolsets.appimage: "1.0.3"` embeds a static runtime and drops the FUSE
   requirement entirely — which is the only version of „runs anywhere with no
   packaging" that is actually true. Proved by running it on a host where
   `ldconfig -p | grep -c libfuse.so.2` is `0`: it came up and stayed up.
6. **DC-32 — `appInfo()` rejected on every first run, on every platform.** Found
   in the main-process log of the first Linux launch: `AppInfo` carried
   `databasePath`, which needs a selected account, so the title bar's version
   request failed on the one screen a new user always sees. The renderer's
   `.catch` is correct and had made the failure invisible for as long as the
   feature has existed; nothing had ever read the field. It is gone.

**A product constraint Linux makes visible.** `safeStorage` on Linux is
libsecret, so **Nexus refuses to create or unlock an account without a running
Secret Service provider** (gnome-keyring, KWallet, KeePassXC). That refusal is
ADR-018 working as designed — no silent PIN-only downgrade — but it means a bare

### DEFECT — a sealed device name bound to a platform the row does not have (2026-08-09)

Found by writing the test, not by running the app, and it is the reason the test
opens the name instead of comparing ciphertext. `deviceNameAad` binds
`platform`, and `openDeviceName`'s contract is that the context must be **what
the server says the row is** — that is what makes a moved ciphertext a visible
failure. The adoption flow sealed ONE name, bound to `desktop`, and wrote it into
both rows: the real desktop row (correct) and the bootstrap row, whose
`platform` is `web` because a client may not write that column. Nothing could
ever have opened the second one. The row is never deleted, so the account's
device list would have carried a permanent unreadable entry — which is exactly
the outcome step 8 exists to prevent, failing silently while every assertion
about the write passed.

**Fixed once, where it belongs:** the scaffolding's name is sealed by the
function that owns the scaffolding, bound to `web`; `register()` seals the
`desktop`-bound one for the row it buys. Same words to the user, two ciphertexts,
because they are two rows read through two platforms.

**Blast radius, checked:** four `sealDeviceName` call sites in the product —
`sync-crypto/enable.ts` (→ `nexus_mk_mint` writes `desktop`), `reconnect.ts` (→
`nexus_device_register` writes `desktop`), and adoption's two. All four now agree
with the row their output lands in. There is **no rename surface anywhere**
(`devices.ts` has only retire and touch), which is where this class will appear
next: a rename must seal against the platform of the row being renamed, and a web
rename and a desktop rename are therefore not the same call. The requirement is
now stated on `WebDeviceInput.deviceName` in the transport, where a future caller
reads it.


### Sync slice 12 — a desktop whose session dies can get back on the account, and the price is the master key (2026-08-09)

*Commits `6e62fb1` (the proof), `e611767` (migration 013 + pgTAP), `66dcc1f`
(the Edge Function + transport), `0271e9c` (the desktop surface). Unpushed.*

**The hole this closes, and why it was mandatory rather than an edge case.**
Verifying an MFA factor revokes **every other session the account holds** — a
measured fact, pinned by `supabase/tests/live/sync-enable.test.mjs`. So a second
computer merely *attempting* to enable sync strands the first one: its
`devices.session_id` names a session that no longer exists, `nexus_session_is_live()`
refuses everything it tries, and the column is immutable both by grant and by the
`devices_guard` trigger (NX202), so it cannot re-point its own row. Meanwhile the
master key is sitting on that machine's disk, openable under its own data key.
The product answer before today was „disconnect and pair again", which for a
one-computer household means *there is nothing to pair with*.

**Why the price is MK and not the second factor.** The obvious fix — let a
stepped-up session mint a desktop row — is wrong twice over, and both reasons are
written into the migration header so nobody re-derives them:

1. **It repeals the policy it sits next to.** `key_wraps_master_key_is_desktop_only`
   treats a live `platform='desktop'` row as authority over `mk_under_kwrap`,
   whose opener K_wrap is derived from the **web password**. „Password + TOTP ⇒ a
   desktop row" is therefore „password + TOTP ⇒ the master key", and the whole
   reason the desktop-only rule exists is that those two credentials are exactly
   what a phisher collects.
2. **It cannot terminate.** A step-up revokes every *sibling* desktop's session
   too, so two computers would take turns rescuing and stranding each other for
   as long as the user kept trying.

So the proof is **possession of MK**: `deriveDeviceRegisterProof` is
`HKDF-SHA256(MK, info = "nexus/sync/device-register/v1" ‖ userId)` → 32 bytes,
deterministic, no clock and no challenge in it — which is precisely what lets a
machine compute it *before* it can reach the server. The sign-in is a single
ordinary `aal1` one.

**Why a stored verifier and not a signature.** An Ed25519 key with a signature
over `session_id` is stronger in the abstract (non-replayable), and it is not
stronger against the threat model here. `private.mk_verifiers` has no grant to
`anon` or `authenticated` and lives outside the schema PostgREST exposes, so the
only readers are a whole-database compromise and the service role — both of which
already win without it. The choice is a one-way value, no new primitive, no new
test vectors. The comparison is **blinded** (`sha256(blind ‖ x) = sha256(blind ‖ y)`
with a fresh random blind), because `=` on `bytea` is a memcmp whose duration
carries the matching-prefix length; the blind uses core `sha256` and not
pgcrypto, because an extension that is present on hosted Supabase and absent
locally is a check that silently stops being made.

**The mint had to be dropped and recreated.** The verifier must be written by the
transaction that mints MK — see DC-24 — so `nexus_mk_mint` gained a fourteenth
parameter, and migration 013 drops the 011 signature rather than adding a
sibling. An account minted without a verifier could never acquire one.

**`nexus_device_register` does four things in one transaction**, and the order is
the argument: it refuses a dead or expired session (NX401), refuses anything that
is not `aal1` (NX405 — an `aal2` caller is a browser stepping up, and a browser
may never own a desktop row), refuses an account with no verifier (NX402),
compares the proof (NX403), then **retires this account's desktop rows whose
session no longer exists** before inserting. That sweep is what stops the 20-row
cap (NX406) filling with the corpses of a machine that has reconnected five
times. It is idempotent: a second call on the same session returns the same row
id rather than a second row.

**The desktop learned that „get back on" is two questions.** `resume` exchanges
the stored refresh token — one request, no password, and the **same `session_id`**,
so the existing device row stays valid. That is the normal case at every single
launch, and the settings card now runs it automatically the moment the status
arrives. Only when it fails does `reconnect` appear: password → K_auth → sign-in
→ proof → a new device row. MK is opened **first**, before any network call, so a
machine whose local wrap is damaged learns it without spending a sign-in. Both
halves write back what they earn — `resume` banks the rotated refresh token
(GoTrue rotates on every use, so not writing it back would make each launch the
last one that could resume), `reconnect` writes the new device id *and* the token.

**`syncCardState` decides whether the form is offered at all**, and the predicate
is now shared with the enable form (`reachable()`): both are refused by main with
`cloud_off` when the stored switch disagrees with the launch, and a form drawn in
that window takes a password for a call that cannot happen. A signed-in computer
is never offered it either — it has a good row and reconnecting would mint a
second.

**Deliberate: main does NOT refuse a reconnect from a signed-in session.** The
renderer will not offer it, but the server-side case where the web app retires
this desktop's row while its session is still live is real, and refusing in main
would make that unrecoverable. Nothing detects that state yet (see below).

**Verified.** `pnpm typecheck` 12/12, `pnpm test` 11/11 tasks (desktop 93 files,
including 12 new `reconnect.test.ts` cases and 7 new service cases), `pnpm build`
4/4, all seven static gates, `SMOKE OK`, `supabase test db` **165/165 across 7
files** (06_device_register is new, 15 assertions), `test:wall` 63/63, and the
live suites **24/24** against the running local stack — including the end-to-end
one that mints, strands the row by signing the session out, and proves the same
computer registers again and retires its own corpse. The single most valuable
assertion in the slice is in `reconnect.test.ts`: the proof sent by `reconnect`
is byte-identical to the one `prepareSyncEnable` handed the mint. If those ever
diverge, every reconnect on every machine fails forever with no symptom.

**What is NOT built here.**

- **Nothing calls `resume` at startup.** Only the settings card does, so a user
  who never opens „Sinhronizacija" stays signed out. That is harmless today
  (nothing syncs yet) and becomes wrong the moment the sync engine exists —
  `resume` belongs in the engine's start-up path.
- **A device row retired from the web is invisible here.** The desktop finds out
  only when a call fails, and today no call is made. The engine will need to map
  that failure onto „offer reconnect".
- **The reconnect form has never been photographed with real state**, for the
  same reason the enable form has not: it needs an enrolled account and a dead
  session, which the sweep cannot produce.
- The 20-device cap has no user-facing management surface; retiring a device is a
  web-app feature that does not exist.

### Sync slice 11 — the desktop can now turn sync on, and the settings page learned to measure itself (2026-08-09)

*Commits `17ca062` (db), `0eb14e9` (transport auth + devices), `b20a1c7`
(sync-port types), `4ef7265` (the desktop surface). Unpushed.*

**What exists now.** Everything between „the user clicks a checkbox" and „this
account has a master key, and this computer holds a copy of it wrapped under its
own data key". Slice 10 built the material; this one built the machine that
carries it.

- **`sync_account` (migration 064, `packages/db/src/sync/syncAccount.ts`).** One
  row, enforced by the schema: the master key wrapped under this device's local
  data key, the account address, the device row's id, the session's refresh
  token, and when it happened. A second row would be a second master key for an
  account that has one, so the table cannot hold two. It is **device-local**, and
  therefore in the restore wipe's documented allowlist — restoring a backup must
  not silently leave the sync account, which is what wiping the local wrap would
  do. `collectionGuard.test.ts` proves `RESTORE_WIPE_TABLES ≡ SYNC_MAP`, so the
  exemption provably also keeps the row off the wire; that closure is why the
  argument is one sentence and not a second hand-maintained list.
- **`packages/sync-transport/src/auth.ts`.** GoTrue as six requests and the
  answers to them — sign in, refresh, list factors, challenge, verify, sign out —
  with no session store and no clock, because which sessions exist and for how
  long is the part with the argument in it and belongs to the caller.
  `AuthRequest`/`AuthPort` **invert** the rule the other two seams keep: an auth
  port adds `apikey` and nothing else. Four of the six calls carry a different
  bearer or none at all (sign-in has none; refresh carries the refresh token in
  the *body*; step-up carries the authorising session's token; sign-out carries
  the token of the session being ended). A port that wrote `Authorization` last,
  as `HttpPort` and `FunctionPort` do, would have signed out the **device**
  session instead of the authorising one — leaving the account enabled and this
  computer locked out of it, with no symptom until the next launch.
- **`packages/sync-transport/src/devices.ts`.** The two writes a desktop may make
  to its own row (`touch`, `retire`) and the one it may not: `session_id` is
  withheld from every client by the grant, which is the reason a revoked desktop
  cannot re-point its row at a new session and rescue itself. Written down here
  because it is also the reason there is no „sign out but stay enabled".
- **`apps/desktop/src/main/sync/`** — seven modules. `config.ts` parses the build
  variables (and `buildCloudEnv` reads them as literal member accesses, because

  `undefined` in a packaged app while working perfectly in dev). `port.ts` builds
  the three ports **or returns `null`** — the whole cloud-off guarantee in one
  branch. `electronFetch.ts` is the single socket. `session.ts` holds the live
  session; `enable.ts` runs the protocol; `service.ts` is what IPC talks to.
- **Four IPC channels** (`sync:status`, `sync:set-cloud`, `sync:enable`,
  `sync:disconnect`), each validated in main, and a settings card that receives
  an address, a device id, a date and four booleans — no token, no key, no wrap,
  and none of the transport's English `detail` strings, which are developer fault
  reports and would eventually be shown to somebody. A refusal crosses as a
  machine code; `strings.sr.ts` maps all 23 of them and is declared `satisfies
  Record<SyncEnableProblem, string>`, so a refusal the protocol grows and the copy
  does not name is a compile error rather than an empty message box.
- **`allowedRemoteOrigins` stopped being the empty literal** it was for the whole
  of 1.0.0. It is now exactly the project's two origins — `https://` for
  PostgREST and the Edge Functions, `wss://` for Realtime — and only when this
  launch has cloud on *and* this build knows its project. It is **read from the
  service**, not computed at the call site, so „a port was built" and „its origin

### Sync slice 10 — the desktop half of the mint, and a live suite that had quietly stopped being run (2026-08-09)

**What exists now.** The material the mint is made of, and the call that carries
it, both as pure code with no origin and no `fetch` in either.

- **`packages/sync-crypto/src/device-name.ts`.** The device-name rule left
  `pairing.ts`, because `devices.name_ciphertext` now has a second writer (the
  mint) and a rule this exact, copied by hand, diverges in whichever copy is
  edited second. It also gained the seal itself — `sealDeviceName` /
  `openDeviceName` under an HKDF subkey of MK, AAD binding the account and the
  platform. Two things are written down rather than left to be discovered: the
  AAD *cannot* bind `devices.id` (the database generates it in the same
  statement that stores the ciphertext), so an operator can permute name
  ciphertexts among one account's same-platform devices — a display defect only,
  since the name a human sees while authorising a pairing comes from the
  handshake transcript; and **a browser cannot read a device name at all**,
  because it never holds MK. The web device list will therefore show when a
  device was added and what platform it is, and not what it is called. That is a
  gap in a feature nobody has built yet, and the alternative — a second
  account-wide key handed to browsers — is a branch of the key hierarchy that
  should not be invented speculatively.
- **`packages/sync-crypto/src/enable.ts`.** `prepareSyncEnable` mints MK,
  generates the Sync Recovery Code and its salt, produces all three wraps
  (`mk/local-data-key`, `mk/web-password`, `mk/sync-recovery`) and the sealed
  device name. It **derives K_wrap itself from the password** rather than being
  handed it, which is the one design decision in the file worth defending: taking
  the key as a parameter means also taking the Argon2id cost as a parameter, and
  those are then two facts that must agree. When they disagree the wrap is stored
  under a cost nothing reproduces and the account's master key is unopenable by
  password forever — silently, discovered on a future device. It costs one extra
  Argon2id, once per account, ever. It then **opens all three wraps again and
  compares to MK**, because two `CryptoPort` adapters exist and one that seals
  correctly but cannot read its own output is a defect whose natural discovery
  point is a user's next device with the only copy of the key already gone.
- **`packages/sync-transport/src/enable.ts`.** The request, every answer the
  endpoint can give (each named, because „confirm your email address" is not
  „turn on two-factor" and a spinner is not a next step), and
  `syncEnableRoundTripProblem` — a **byte comparison** of what the server stored
  against what the desktop sent, which needs no key and so can run after K_wrap
  and the recovery key are gone. The two facts compose: these bytes open to MK,
  and the server holds these bytes.
- **A second port type, `FunctionPort`.** `HttpRequest.path` is documented as
  living under the PostgREST root and an Edge Function does not, so reusing it
  would mean either a port that inspects paths or a caller writing
  `/functions/v1/…` into a field whose contract says it never contains one.

**Measured against the running stack, not assumed.** `kind=in.(a%2Cb)` — the
list separator arrives percent-encoded, because `filterValue` encodes every
value — parses into two members and excludes the third row. „PostgREST decodes
the query string before parsing" being true of `eq.` does not make it true of a
list, so it was probed directly and is now pinned by a live test.

**The finding that was not the task.** The transport's live suite could not pass
against the current schema. Migration 010 tightened `key_wraps_desktop_only`'s
`WITH CHECK` to require a live `platform = 'desktop'` device bound to the
caller's own session for **every** write to `key_wraps` — `ck_under_mk`
included, not only the master-key slots — and the suite's fixture minted an
`aal2` token with a random `session_id` and no desktop device. Every one of its
twelve tests died in `beforeAll`. Nothing noticed because the suite skips
without a running stack locally, and CI has not run since the migration landed
(it is in the unpushed commits). The fixture now registers the desktop device
**with the service role**, which is the only way it can be: `grant insert` on
`devices` withholds `platform`, so no client can declare itself a desktop, and
`nexus_mk_mint` is the one writer that can. This is DC-21 below.

**Also learned, from the same run.** PostgREST refuses a bulk insert whose
objects do not carry identical key sets (PGRST102, „All object keys must
match"), and the two master-key slots differ by exactly `kdf_salt`. It does not
reach the `sync-enable` body — that is a JSON body for an Edge Function, not a
PostgREST insert — but it reaches anything that ever writes those two rows side
by side.

**What is still not built** (the desktop application half): the two-session
sign-in dance in the forced order, the main-process auth client, the cloud-off
gate in front of all of it, the IPC channels, and the screens that show the
Recovery Kit once and never again. — *All of it was built in slice 11 above,
later the same day; this paragraph is the state as of this slice.*

### Sync slice 9 — the mint became executable, and three of my own gates turned out not to gate (2026-08-09)

**What exists now.** `public.nexus_mk_mint` (migration 011) and the `sync-enable`
Edge Function are the whole server end of „an account gets a master key". The
function authenticates two tokens, shapes the payload and carries it; the SQL
decides everything, reading `auth.sessions`, `auth.mfa_amr_claims`,
`auth.mfa_factors` and `auth.users` directly rather than trusting any claim the
caller presents. `supabase/README.md` §6.6 holds the three decisions that must
not be quietly reversed — no adoption, `commit_tag` is not a fingerprint, the
mint session is not the sync session.

**The desktop client half is NOT written**, so no account can sync yet. That is
the next piece of work and it is the last thing between here and a first
end-to-end sync.

**Seven guards, proved by removing them one at a time.** Each guard in the mint
was deleted from a copy of the function, the suite re-run, and the failing
assertion checked by name. Six behaved. The seventh — the `aal2` check itself —
**produced no failure at all**: the fixture session it was supposed to be tested
by also had no `mfa_amr_claims` row, so the AMR guard was quietly answering for
it and assertion 6 read as „an aal1 session cannot mint" while proving something
else entirely. Giving that fixture a `totp` claim, so the assurance level is the
only thing wrong with it, made the mutation go red. This is DC-19 below.

**Two more gates were found not gating, both of them mine.** The RLS auditor's
`search_path` rule sliced a function header at the first `$` — but its own
comment-stripper replaces `$` with a space, so the slice never matched and the
rule fell back to a blind 400-character window, which the 13-parameter mint
signature overflowed. And the pgTAP plan-count checker did not know `set_eq`, so
a file using it looked over-planned, which invites the fix „lower the plan"
rather than „the helper is missing from the list".

**Three defects fixed on the way, none of them reported by anyone.**

- **`key_wraps.kdf_params` had a floor and no ceiling.** `kdf.ts` refuses to
  derive outside a range because the parameters arrive from a server this design
  treats as hostile — so the schema was accepting wraps no client would ever
  open, and for the two `mk_*` slots that is a master key with no route back.
  Parallelism is the sharp case: raising `p` at fixed `m` leaves the honest cost
  alone and hands a many-core attacker a proportional speedup, so a large value
  *weakens* the wrap while looking, in the row, like a stronger one. Migration
  012 adds `key_wraps_kdf_params_ceiling`, written with `CASE` because `and`/`or`
  have no guaranteed evaluation order in Postgres and a cast can legally run
  before the type guard that was meant to divert it. DC-20 below.
- **The two Edge Functions were about to hold two copies of five security
  controls.** `readBounded`, `callerAddress`, `declaredLengthOk` and the decoders
  moved to `supabase/functions/_shared/http.ts`, and `pair-complete` now imports
  them instead of owning them. 20 tests under `pnpm test:wall` cover the
  behaviours that have a wrong version which looks right — `hops[0]` instead of
  the rightmost forwarded hop, a body cap that abandons the stream instead of
  cancelling it. A DC-02 instance, caught before the second copy existed.
- **`declaredLengthOk` parsed `content-length` with `Number()`**, which is a
  JavaScript literal parser: it read `0x10` as 16 and `1e9` as a billion. HTTP
  spells the field `1*DIGIT`. No security consequence — the real cap counts bytes
  off the stream — but a courtesy check that quietly means something else is how
  a reader concludes the budget is enforced there.

**A platform fact nothing in our code reads as depending on.** Measured, then
pinned: **verifying an MFA factor revokes every other session the account
holds.** The stepped-up session survives, sessions signed in afterwards survive,
everything from before is answered `403` by `/auth/v1/user`. It forces the order
the desktop must sign in — step up first, device session second — and it was
found the only way it could be, by six live tests failing with a `401` that said
nothing about ordering.

**What this leaves open, and it is a real gap.** That revocation is not confined
to one machine. Enabling sync from a *second* desktop revokes the first one's
session, and a `devices` row is bound to a `session_id`: the row survives, the
session does not, and the desktop's next sign-in produces a different
`session_id` that no longer matches its row — so it fails
`private.nexus_session_is_live()` and reads nothing, forever. **Re-binding a
device row to a fresh session is device lifecycle and is unbuilt.** Nothing in
the schema is wrong; there is simply no path, and a desktop cannot currently
recover from this on its own. It must be designed alongside pairing, because
pairing is the other thing that writes a `devices` row.

**Coverage.** pgTAP 149 assertions across six files (was 143); `pnpm test:wall`
63 static tests across four files (was 39); a new `pnpm test:live` with 14 tests
that run the real function against real GoTrue sessions — real password sign-ins,
a real TOTP factor enrolled and verified, a real step-up. CI runs all three.

### Sync slice 8 — the wire, measured against a running server rather than a spec (2026-08-09)

`@nexus/sync-transport` is the layer between „what to send" (`@nexus/sync`) and
„what it is sealed with" (`@nexus/sync-crypto`): column names, `bytea` spelling,
paging, which SQLSTATE means what, and the Realtime frames. Nine source files,
110 tests, and — this is the point of the slice — **every wire-level rule in it
was measured against the running local Supabase, not derived from documentation.**
Four of them turned out to contradict what a careful reader would have assumed.

**It holds no origin, no key, no `fetch` and no `WebSocket`.** Requests are built
and handed to an injected `HttpPort`; Realtime frames are produced as strings for
a socket the caller owns. This is the same port-injection shape as `CryptoPort`,
and it is what makes cloud-off structural here: a desktop with cloud off never
constructs a port, and there is nothing in the package that could go looking for
one. The whole of „reach the network" is nine lines in the live test — an origin,
two headers and a `fetch` — and that file carries a named exemption in
`scripts/check-egress.mjs`. `@supabase/supabase-js` is deliberately absent: it is
four clients in one, each with its own `fetch` and socket, it would land in the
Electron main process beside the SQLCipher key, and it leaves the one genuinely
fiddly part — how `bytea` is spelled — entirely to the caller anyway.

#### The four measurements that a spec would have got wrong

1. **A filter value is percent-encoded and NEVER double-quoted.** The instinct is
   to quote, because PostgREST documents quoting for values containing reserved
   characters and an object id here can contain a comma, a dot, a quotation mark,
   a backslash, U+001F (the `note_updates` separator) or nothing at all (the six
   per-profile singletons). **The instinct is wrong and it fails silently.**
   Across twenty-one id shapes the bare percent-encoded form matched exactly one
   row every time and the quoted form matched **none of them, including the plain
   one** — quoting does not escape the value, it becomes part of it.
2. **A PATCH matching no row is HTTP 200 with `[]`.** Not an error at any layer:
   PostgREST is content, the trigger never fires, and a client that does not read
   the body records a successful sync of a row that was never written. Combined
   with (1), the failure mode is a device that appears to be syncing and is not.
   `pushRow` reports that shape as `absent`, and it is one of the two mutations
   run against the suite to prove the tests can fail.
3. **Upsert is closed to clients, and the schema is why.** PostgREST's
   `resolution=merge-duplicates` compiles to `ON CONFLICT DO UPDATE SET <every
   payload column>`, which needs UPDATE on the four identity columns migration
   002 deliberately withholds — so every upsert is `403 42501` for
   `authenticated`, on `sync_objects` and on `sync_state` alike. Push is
   therefore two verbs: POST for a creation (version 1), PATCH filtered by the
   four-column PK for an update. Migration 003's comment claimed the upsert path
   was a client's; it has been corrected to say it is `service_role`'s.
4. **`max_rows = 1000` truncates a response without saying so.** So „fewer rows
   than I asked for means the end" is wrong and wrong silently — there is no
   header separating „that is all there is" from „that is all you may have at
   once". The loop rule that survives any cap: keep pulling while rows arrive,
   stop on an EMPTY page.

#### A real defect, caught by running the walk instead of reading it

`pullPage` subtracted the cursor overlap on **every request**. A walk that
advanced to the last row of a page and asked again had 64 taken off the number it
had just moved to — so with any page limit at or below the overlap **the window
never moved and the walk did not terminate**, and above it every page of a full
hydration re-read 64 rows instead of once at the start. The unit tests passed;
the live test with `limit = 2` hung.

Root cause is a granularity error, not an arithmetic one: the hazard the overlap
defends against is „a row numbered before my STORED watermark committed after I
read past it", which is a fact about the stored watermark, so **the overlap
belongs to a walk, not to a request.** Fixed by splitting `pullWindow(cursor)`
(called once per round) from `pullPage(…, fromSeq, …)` (literal), with the
regression test that would have caught it.

#### Migration 008 — `sync_state.updated_at` was a claim, not a fact

Found while writing the cursor client. Migration 001 comments the column „when
the device last synced"; migration 002 granted `authenticated` UPDATE on it. Those
two sentences do not describe the same column — a client-written timestamp is the
client's claim about its own clock, on the one value here a human might read as
evidence that a device is alive. And nothing wrote it: `default now()` fires on
INSERT only, so it would have sat at „when this cursor row was created" while
reading as „last synced" — populated, plausible, monotonically wrong, which is
the hardest failure shape to notice.

Migration 003 had already made this exact call for `sync_objects`. Migration 008
applies the same rule to the other table that carries the column: a
`BEFORE INSERT OR UPDATE` trigger stamps it, and the grant is revoked. **Both
halves are needed** — revoking alone freezes the column at its insert-time
default, which is the „populated and wrong" state; the trigger alone leaves a
client able to overwrite it. Both are asserted, and both assertions were proved
able to fail by removing the trigger and re-running (`00` test 22 and `02` tests
29–30 all went red).

#### The cursor race, found by reading the file back

Two browser tabs of one device share a `devices` row and therefore share every
cursor in it. Both miss on the PATCH, both POST, one loses with `23505`. The code
reported that as `unavailable` — a server problem — and the loser's `lastSeq` was
never stored. „The row exists, call it done" is the tempting repair and is false:
the winner wrote ITS value, not ours. The fix re-issues the PATCH, which now
matches because the row exists; once, not in a loop, since nothing deletes from
this table. Proved live by a port that creates the row out of band between the
PATCH and the POST, so PostgREST raises a real 23505 against a real unique index.

#### The signal is Broadcast, not `postgres_changes`

Migration 006 walls `realtime.messages`, and `postgres_changes` would need a
publication over `sync_objects` — i.e. a second, parallel authorisation path over
the same rows. `SignalSession` is a state machine with **no socket and no clock
in it**: it produces frames and consumes text, and the caller owns both. Topic
`realtime:nexus:<user_id>`, `vsn=1.0.0` (2.0.0 frames are arrays), `private:true`
plus `access_token`. There is no token-refresh frame — a new token means a new
session over a new socket, because a refresh frame is a way for a live socket to
outlive the authorisation it was opened under. The hint carries only `profileId`
and collection names: facts the server already stores in the clear.

#### The live suite now actually runs, in the one job that can run it

Two things had to be true for the measurements above to keep being true, and
neither was.

- **Turbo hides every environment variable a task does not declare.** So with
  all four `NEXUS_LIVE_*` set in the shell, `pnpm test` still reported the live
  file as *skipped* — which reads as „ran, nothing to do" rather than „could not
  see your server". `turbo.json`'s `test` task now declares them, as `env` and
  not `passThroughEnv`, so a run with a server and a run without one are
  different cache keys instead of one shared cached result.
- **CI ran pgTAP and nothing else against the stack.** The `database` job starts
  a full Supabase and then used it only for `supabase test db` — so every
  PostgREST-level rule in this slice was proved once, on my machine, and never
  again. The job now installs Node, reads the stack's own keys out of
  `supabase status -o env`, and runs the transport suite against it. In the
  `verify` job the same suite skips itself, correctly; that is exactly why it
  could not be the only place it is mentioned.

**Also in this slice.** `@nexus/sync` now imports `@nexus/sync-crypto/web`
rather than the root barrel, so nothing in the sync path can pull `unwrapKey`
into a browser's module graph transitively. Two `eslint-disable-next-line
no-restricted-globals` directives were removed from the live test: that rule is
not configured anywhere in this repo, so the directives named a rule that does
not exist and read as an assurance nothing was making — the real permission is
the egress allowlist, and the comment now says only that.

*Verified: pgTAP 109/109 against Postgres 17 (106 + 3 new), static 36/36,
typecheck 12/12, turbo test 11/11 plus root 148, lint 12/12 (2 pre-existing
warnings), build 4/4, `SMOKE OK`, seven static gates, db suite re-run on restored

### Sync slice 7 — the master key stopped being a promise about the bundle (2026-08-09)

**The rule that was only written down.** `kdf.ts` says the browser gets
`deriveWebAuthPassword` (K_auth) and never `deriveWebPasswordKeys` (K_auth **and**
K_wrap), so it cannot open the server-held master-key wrap. That defence was real
and it was *entirely* a fact about which functions the web bundle imports — one
stray import, one dependency re-exporting the package barrel, and MK is one
`unwrapKey` call away, because the wrap is a row of the caller's own account that
every policy happily served.

**Server half — `key_wraps_master_key_is_desktop_only`.** A second restrictive
policy on `key_wraps`, on top of the session gate, keyed on whether a live
`devices` row calls the session a `desktop`. `devices.platform` carries that
weight because no client may write it: a client-inserted row takes the default
`web`, and the only writer that can state `desktop` is `pair-complete` under the
service-role key after a completed handshake. „Desktop" therefore means, exactly,
*vouched for by a device that already had the keys* — the strongest sentence
anything here can make, since nothing in HTTP attests what program sent a request.

**The two halves differ, and that is the design, not an oversight.**

- **READ confines `mk_under_kwrap` only.** `ck_under_mk` is precisely what a
  browser is supposed to hold (it gets those through pairing). `mk_under_src`
  stays readable, because confining it would break the one flow it exists for: a
  brand-new desktop recovering an account has no device row yet — obtaining one
  is what it is trying to do. That costs nothing against the threat, because its
  opener is the Recovery Kit code and the web password does not yield it. This
  is the point the earlier `supabase/README.md` recorded as a blocker; the answer
  turned out to be that the rule was too coarse, not that it was premature.
- **WRITE confines both `mk_*` kinds.** A password-only session never needs to
  read what it destroys: `nonce`, `wrapped` and `commit_tag` are all in its
  column grant, so overwriting `mk_under_kwrap` locks every real device out of MK
  and overwriting `mk_under_src` removes the way back. Both are unrecoverable and
  neither leaks anything — the shape of an attack nobody thinks to test for.

**Client half — `@nexus/sync-crypto/web`.** The rule as a capability list rather
than a comment. It exports `deriveWebAuthPassword` and not the other two, and
omits `wrap.ts` entirely: a browser neither mints keys nor opens wraps.
`rewrapMasterKeyForEmailChange` moved to a new `rewrap.ts`, and that is
load-bearing rather than tidying — it was the single import edge that pulled
`unwrapKey` into the browser's module graph *behind* the one KDF function a
browser legitimately calls. With it gone, the third forbidden name is
**unreachable** from the web barrel rather than merely unexported.

**Four layers, because the first three each have a way out.** (1) the barrel;
(2) the module graph with no path to `wrap.ts`; (3) `no-restricted-imports` over
`apps/web`; (4) `scripts/web-key-surface.test.mjs`, which reads the source and
does not care what ESLint was told. Layer 4 walks the web app's whole **workspace
dependency closure**, because the claim is about the BUNDLE and the bundle
contains whatever `@nexus/ui` or `@nexus/core` imported on its behalf; it also
carries a vacuity guard (the closure contains `@nexus/web` and `@nexus/ui`, and
more than 50 files were actually scanned), since „no offender found" is what an
empty closure produces too.

**Deliberately NOT a grep of `apps/web/dist`,** which was the obvious shape and
is unsound in both directions: a minifier renames every binding, so the names are
absent whether or not the code is, and an inlined helper has no name at all. The
import graph is the thing that is true, and it is true before the build runs.

**Two defects found by running the gates rather than reading them.**

1. The ESLint layer first used `patterns.group`, which matches the way
   `.gitignore` does — the bare package name covers `/web` too, and gitignore
   cannot re-include a path under an excluded directory, so `!@nexus/sync-crypto/web`
   did nothing and the rule refused **the one import the web app is supposed to
   make**. That failure does not read as a rule being too broad; it reads as the
   barrel being wrong, and the repair somebody reaches for is an `eslint-disable`
   on the exact line the rule exists for. Now `paths`, with the entry list
   derived from the package's own `exports` map so a future subpath goes red on
   the commit that adds it. **This is DC-15.**
2. The graph walker's first import regex was unanchored, so it matched `from
   "…"` inside prose and reported the English phrase *"non-empty"* as a
   third-party dependency of the web barrel. Anchored to statement starts.

against Postgres 17, static 36/36, typecheck 11/11, turbo test 10/10 (2 692 core,
2 111 db, 1 592 desktop, 201 sync-crypto, 102 ui, 82 sync, 62 web, 31 sync-port)

reverting it.*

### Sync slice 6 — a version that cannot skip, an epoch that names a key, and a clamp that had to go (2026-08-09)

Three corrections to the contract, each of which came from running something
rather than reading it, and one finding that says a whole layer is undesigned.

**The version is now a compare-and-swap, not a monotone counter.** Migration
003's rule was „strictly increases"; a client that observed version 5 and wrote
9 — a drifted counter, a `max(local, remote)` that read the wrong side, any
ordinary bug — silently overwrote versions 6, 7 and 8 that it had never seen.
A LOST UPDATE, accepted by the server, with no error anywhere. It is now
`new.version = old.version + 1` (NX001), under which a write that did not see
the current row cannot be expressed at all. That retired the old bounded-step
rule outright: with the space unjumpable, „steps of at most 65 536" was an
argument about how much of an impossible attack to permit, and `MAX_VERSION_STEP`
is gone from `@nexus/sync` with it. A creation is exactly version 1 (NX002) —
and that rule had to be made conditional on a primary-key probe, because
**testing showed a BEFORE INSERT trigger fires before `ON CONFLICT` detects the
conflict**, so every upsert push of an existing row arrived at the INSERT branch
carrying an UPDATE's version. A flat „a creation is version 1" would have broken
every push, and would have looked like a version bug rather than a trigger bug.

**A content-key epoch must now name a key that exists (NX007).** `ck_epoch` is
writable by any session on the account, may only rise, and `smallint` tops out
at 32 767 — so a stolen session could set one row to the ceiling and no future
rotation could ever bring a key up to meet it. The row would be unopenable
forever, by everyone, including the owner. Bounding the step was strictly weaker
(the same attack, a few thousand statements instead of one). Naming the epoch
against the set of wraps that actually exist makes it unrepresentable. Finding
that also surfaced a hole nobody had listed: `key_wraps` could hold only ONE
content-key wrap per profile, while `ck_epoch` exists precisely so two
generations are live during a rotation — so a rotation would have destroyed
every row the re-encryption pass had not yet reached. `key_wraps` now carries an
`epoch` column, and the client's `WrapContext` carries it into the KEY
DERIVATION, so asking for epoch 2 and being handed epoch 1 fails at the
commitment check instead of opening perfectly and then decrypting nothing.

**That rule also had to MOVE, and the reason generalises.** As a BEFORE trigger
it fired before RLS evaluated `WITH CHECK`, so a cross-tenant insert was told
„this epoch has no content-key wrap" — a fact about data the caller is not
allowed to know exists — instead of 42501. It is now a separate AFTER trigger.
**Tenancy decides first:** a data-integrity rule evaluated under the caller's own
visibility is only meaningful once the caller is established as entitled to the
row, and in PostgreSQL the only place after `WITH CHECK` is an AFTER trigger.

**The HLC's forward clamp lost its second use.** `clampRemoteHlc` was documented
as having two callers: protecting this device's own clock, and deciding the
stamp a received row is STORED with, the second taking the server's attested
receipt time so every device computes the same ceiling. The second is not
determinable and the file now says so. A field stamp travels inside the row
ciphertext and is carried forward by every later version, but `updated_at` is
re-stamped on each version — so a device that pulled the stamp at version 3
clamps it against `updated_at(v3)` while a device that first sees it inside
version 7 clamps the same stamp against `updated_at(v7)`. Two ceilings,
permanently, because each device stores what it computed: the exact divergence
the clock exists to prevent. A received stamp is now stored exactly as it
arrived, the clamp is private to the module, and `hlcExceedsDriftWindow` is what
the engine will use — at send time to refuse to seal a write from a wrong clock,
at pull time to name the peer stamping from the future. **Never to rewrite a
stamp.**

**What shipped alongside:** `wire.ts` (the row as it crosses the wire, and a
parser that rejects unknown keys — a field the client does not understand but
stores and re-emits is a channel the server controls), `push.ts` (`planPush` —
refusals are returned by name, never thrown, so one malformed id does not cost
thirty-nine other objects their round trip) and `pull.ts` (`applyPull` — the AAD
is rebuilt from the SERVER'S OWN CLAIM, which is what turns every clear-column
rewrite into a visible failure; a missing key HOLDS the cursor, an AEAD failure
ADVANCES past and quarantines, because one is worth retrying and the other will
answer the same way forever). Verified end to end against a real PostgREST: the
error codes reach the client as HTTP 400 with `code`/`details`/`hint` intact.

**THE FINDING, and it is the more useful answer: the apply path is undesigned,
and eleven places already need it.** `COLLECTION_DERIVED` carried one entry —
`tasks.completed_at` — under a doc claiming it listed the columns bound to
another column by a CHECK. Probing the REAL schema found **eleven table-level
CHECKs over synced collections that read two columns which both travel as
fields**: `cards` (three, all pairing `kind` against the column that kind
requires), `focus_sessions` (`ended_at > started_at`), `calendar_settings`
(the semester's two ends), `dashboard_settings` (two, the wallpaper's three
columns holding one fact), `fin_transactions` (two, a transfer that is its own
counter-account and a transfer with a category), `habits` (a unit with nothing
to measure) and `fit_measurements` (a reading with no unit). Field-level LWW
decides each column alone, so two honest edits merge into a row **SQLite refuses
to write** — not wrong, unappliable. Derivation, the answer for
`tasks.completed_at`, is unavailable for every one of them: each pairs two
columns a user typed, and a column that cannot be rebuilt must not be dropped
from the field map.

What is BUILT is the ledger and its gate — `COLLECTION_COUPLED` in
`@nexus/sync`, checked against the real schema by `@nexus/db`'s
`collectionGuard.test.ts` in both directions, so a migration that introduces a
twelfth fails on the day it is written. What is NOT built, and is now the apply
path's defining requirement: **a deterministic repair.** Every device must
compute the same repaired row from the same merged state — one that repaired
differently would diverge over a row neither could fix — and a row it cannot
legally write needs quarantining and surfacing rather than an exception. See
DC-14.

pgTAP 99/99 against Postgres 17, static 33/33, typecheck 11/11, all package
tests green, lint 11/11, build 4/4, `SMOKE OK`, seven static gates.*

### Sync slice 4 — the sweep, and the journal it will read (2026-08-08, late)

`mergeRowState` merges FIELD BY FIELD, so every field needs its own HLC stamp,
and nothing in the database holds one — a task row has a single `updated_at` for
the whole row, which is exactly the granularity field-level merge exists to
avoid. **`sweepRow` is the pure half of the answer:** given the row, the previous
`RowState` and a clock, it returns the next `RowState`, or `null` when the change
turned out to be no change. No SQLite in it, so it is testable without a database
and reusable by the web client, which has none.

**It diffs rather than re-stamping, and that is the whole design.** `applyEdit`
stamps every field it is handed on purpose — its own header argues that „I looked
at this and it is still X" is a real assertion, which is right for a user pressing
Save. It is wrong for a sweep, because a sweep does not know whether a user
pressed anything: the trigger that queued the row fires on ANY update, including
a bulk re-save, a migration or a restore that rewrote it with identical values.
Stamping there would let a no-op write beat a genuine edit made on another device
a second earlier, and the user would watch their typing vanish.

**Three columns never travel**, and the guard proves it for all fifty-four
collections: `profile_id` (already decided by the key that opened the row),
`updated_at` (a shadow of the merge itself — LWW on it would be circular) and
`deleted_at` (the tombstone is already a stamped field; syncing both would let a
row be deleted and not deleted at once). `tasks.completed_at` joins them for a
sharper reason: migration 002's CHECK binds it to `status`, so merging the pair
independently produces a row **SQLite refuses to write** — the row would not be
merely wrong, it would be unappliable.

The three absence cases are stated rather than left to fall out: a row gone and
never known says nothing (a tombstone for an object nobody has a record of is
noise they must keep forever); a row gone and already tombstoned says nothing
(which is what makes the journal safe to resolve twice); and an undelete clears
the tombstone WITHOUT re-asserting every field, so an edit made elsewhere while
the row was deleted still wins.

**ADR-083 records the other half — the journal — and it is designed but not
built.** It is a DIRTY SET rather than a log (self-healing and idempotent by
construction), written by TRIGGERS rather than by store calls (DC-08: dozens of
store methods write to synced tables and every one is a chance to forget; a
trigger cannot be forgotten by a method nobody has written yet), and the reason it
cannot be an `updated_at > last_seen` sweep instead is hard deletes — a deleted
row has no `updated_at` to be greater than anything, and a delete that never
reaches the other device is the worst sync bug there is, because the user's
evidence for it is that the thing they deleted came back.

The trigger table in that ADR was PROBED off the real schema rather than assumed
— forty-eight synced tables carry their own `profile_id`, thirteen reach it
through a parent, and the exact foreign key of each is written down. The first
guess had been wrong once already (`task_dependencies` has `blocker_id` and
`blocked_id`, never a `task_id`), which is why it was probed.

### Sync slice 3 — the collection map became code that can be falsified (2026-08-08, late)

ADR-082 answered *what syncs and as what* in prose. `@nexus/sync` is that answer
in code — and, more to the point, in a form the schema itself can contradict.

**The problem the arrangement solves.** ADR-082's first decision was that the set
of user content is DERIVED from `RESTORE_WIPE_TABLES` and never written out a
second time: a table added in six months would be caught by the restore guard and
sail straight past sync, and nothing would look wrong (DC-07, DC-08). But that
list lives in `@nexus/db`, which is SQLite and therefore Node-only, while the map
has to be readable in a browser tab. So the map is **declared** portably in
`@nexus/sync`, and `@nexus/db` carries the **guard** that makes the derivation
real — `collectionGuard.test.ts` reads `sqlite_master` and `RESTORE_WIPE_TABLES`
and fails until the two agree.

**It checks the shapes, not just the table list.** A table list is the easy half.
Every table the map demotes to a field of its parent declares WHICH shape it is,
and the guard checks that claim against the columns that actually exist:

- a `join` row must carry **no data column at all** — every column an id, a key,
  or a timestamp. If one grows a column somebody types into, it has become a row
  a user can point at, which by ADR-082 §2 makes it a collection;
- an `ordered-child` must really be an array inside its parent — a NOT NULL
  parent key and an INTEGER `position`, deliberately not the fractional rank
  migration 062 gave the hand-orderable scopes, because this array is replaced
  whole and so never has two writers to merge;
- and no table called a collection may be join-shaped, which catches the mistake
  in the other direction.

**It found one immediately.** I had `task_dependencies` hanging off a `task_id`
column. Migration 029 named them `blocker_id` and `blocked_id`, and there is no
`task_id` — the guard refused it on the first run. The edge now hangs off the
BLOCKED task, because that is the one the user has open when they say what is
holding it up: the edit and the object have to be the same object.

**Every classification carries its argument, and the length is enforced by kind.**
„A deck is named, opened and edited" is a complete reason. What needs a paragraph
is anything a reader would not have guessed — a row demoted to a field, a table
that syncs nothing, and the one collection that is not a field map — because
those are the entries somebody will one day want to overturn, and they must find
the argument here rather than reconstruct it. A test enforces exactly that split.

**Three open questions are recorded IN the module and asserted non-empty**, so
answering one is a deliberate deletion rather than a quiet disappearance:

1. `canvas_boards.scene` is one opaque Excalidraw document merged by whole-field
   LWW, so two people drawing on the same board concurrently lose one side's
   strokes entirely. Excalidraw's elements carry their own version nonces and are
   built to merge element-wise; doing that means the scene stops being an opaque
   field, which overturns `canvasScene.ts`'s central decision. **Decide before
   CANV syncs, not after.**
2. `note_versions` must carry its own snapshot bytes, because `note_snapshots` is
   derived and a device that never compacted at that point has nothing to point
   at.
3. `notifications` sync so a dismissal travels — but one generated independently
   on two devices from the same source arrives twice under two ids. Either
   generation becomes deterministic or the apply step dedupes.

`@nexus/db` gained `@nexus/sync` as a dev dependency only: the guard is a test,
and the database has no reason to link a sync engine at runtime.

**Then the same guard was pointed at identity, and found three shapes where I
had assumed one.** Forty-four collections identify an object the ordinary way, by
a UUIDv7 the row owns. Four carry a NATURAL key instead — `instance_id` for a
dashboard placement, `(note_id, seq)` for one Yjs update, `(profile_id,
module_id)` for a feature flag, `(profile_id, day)` for a body measurement. And
**six are per-profile singletons** whose entire primary key is `profile_id`
(`ntf_settings`, `study_settings`, `calendar_settings`, `dashboard_settings`,
`fit_targets`, `fit_body_profile`), so once that is taken out there is nothing
left to identify them: the collection holds exactly one object and its id is the
empty key. The transport has to handle that for real rather than treat it as a
hole in the map.

`profile_id` comes out of every identity deliberately — which profile a row
belongs to is already decided by the content key that opened it, and putting it
on the wire would say the same thing twice. The guard asserts each declared
identity equals the real primary key minus `profile_id`, and names the six
singletons as a LIST rather than a count, so a seventh has to be somebody's
decision.

**One residual risk falls straight out of it**, recorded now rather than
discovered later: a natural key is metadata in the clear, so an untrusted server
learns which modules exist, which notification sources are configured, and on
which DAYS the user measured themselves — without decrypting anything. Same class
as the creation time UUIDv7 already leaks (ADR-082 §3.4), one step worse because
the value is meaningful rather than a timestamp. Either the object id becomes a
keyed hash of the natural key, or the residual list says so plainly.

### Sync slice 2 — ordering stopped being a number (2026-08-08, late)

**Why this came first, before a line of the sync engine.** ADR-082's survey of
all 71 tables produced six hazards that break a naive field-level merge, and the
first of them was not a bug in the sync design — it was a defect in the *shipped*
schema that sync would have made permanent. Since migration 022, every
hand-orderable scope has been a column of integers spaced 1024 apart. An insert
between two neighbours took their midpoint; when the gap ran out, `renumberScope`
rewrote **every row in the scope**.

On one machine that is only expensive. Across two it is **lossy**, and no merge
rule can rescue it: a renumber is a mass UPDATE that carries no information about
what the user actually did, so two devices that each reorder the same list produce
two mass UPDATEs and last-writer-wins keeps one and silently discards the other
person's reordering. Worse, migration 022 back-filled `position NOT NULL DEFAULT 0`
onto every task that already existed — for that whole corpus there was not even a
tiebreak. Fixing this **after** the first row syncs would be a migration of every
task on every device, coordinated across a network. Fixing it now is a local
rewrite of a column nothing outside the machine has ever seen.

**What landed (schema 62).**

- **`packages/core/src/order/rank.ts`** — a fractional rank: a string over
  `0123456789abcdefghijklmnopqrstuvwxyz` read as `<head><integer digits><fraction>`,
  ordered by plain lexicographic comparison. Between any two distinct ranks there
  is always another one, so a move is **always** a single-row write and the only
  row two devices can disagree about is the one that moved. That is a property of
  the representation, not a promise about the code.
  - **Base 36, lowercase only** — not the base 62 the literature uses. The
    alphabet is ASCII-ascending, so JavaScript's `<`, SQLite's `BINARY` and a
    UTF-8 byte comparison are the same order; with no uppercase in it, a stray
    `COLLATE NOCASE` anywhere in the schema cannot fold `a` onto `A` and corrupt
    the order. Slightly longer keys, one whole failure class removed.
  - **The integer part is not decoration.** The first attempt was a pure fraction
    and its own property test killed it: appending converges on `zzz…` and costs a
    character every five rows, so a thousand appends produced a 201-character key.
    With an integer part an append is an increment — five characters cover a
    million rows, verified at 10,000 appends and 10,000 prepends.
  - **`rankForInteger(n)`** converts an old integer sort key exactly and
    row-locally, because a rank's integer part IS a signed base-36 number:
    `rankForInteger(n) < rankForInteger(m)` exactly when `n < m`. A property test
    walks `rankAfter(rankForInteger(n)) === rankForInteger(n + 1)` across ±2000,
    through zero and both magnitude boundaries.
  - 33 tests, most of them properties rather than examples: 10,000 random moves in
    one scope with insertions and deletions, 2,000 splits at the same spot, and a
    seeded PRNG so a failure can be re-run.

- **Migration 062** — `position INTEGER` became `rank TEXT` on the five scopes a
  user can point at and drag: `tasks`, `task_lists`, `task_sections`,
  `dashboard_sets`, `dashboard_widgets`. `fit_routine_items` and `fit_workout_sets`
  were **deliberately left as integers**: by ADR-082's Decision 2 they are a FIELD
  of their parent, replaced whole, so they never have two independent writers to
  merge. A rank there would express what the array's own order already says.
  - `ADD COLUMN` + back-fill + `DROP COLUMN`, **not** a table rebuild — four of the
    five are referenced parents, and rebuilding one re-arms the hazard migration
    038 documents at length. The cost is that `rank` cannot carry a CHECK (SQLite
    cannot add one), so the DEFAULT is a *valid* rank rather than the empty string:
    a raw insert that forgets the column produces a row at the top of its scope,
    never one whose sort key is unrepresentable.
  - The back-fill preserves each scope's exact prior order **including its
    tiebreaks**, so a scope whose positions were all `0` keeps its `created_at, id`
    order rather than acquiring a new arbitrary one.

- **`renumberScope` is gone** — not replaced, deleted, along with
  `TASK_ORDER_GAP`, `positionBetween`, and the retry that existed to recover from a
  gap running out. The case cannot arise, so the code that handled it should not
  exist.

- **The archive format went to `1.39.0`** with an era flag `writesOrderRanks`,
  built on the `writesClozeNumbers` precedent (a value whose MEANING changes rather
  than one that is absent). An archive written before it carries `position` and is
  converted on the way in; one written at or above it carries `rank` and is
  validated with `isRank`. An old backup restores its order byte for byte.

**The claim the whole scheme rests on is tested against a real database**, not
argued: a migration test writes ranks spanning both halves of the integer space,
several magnitudes and a fraction between two adjacent integers, inserts them
scrambled, and asserts SQLite's `ORDER BY rank` equals JavaScript's own sort of
the same strings — and that the shared order is the order they were built in, so
the two engines are not agreeing about something wrong.

**Verification.** `pnpm typecheck` 10/10, `pnpm lint` 0 errors (the two documented
`exhaustive-deps` warnings), `@nexus/db` 2070 tests in 59 files green, `@nexus/core`
2692 green, and all seven static gates clean.

### Sync slice 1 — the wall run, the boundary built, the port made real (2026-08-08 evening)

> Docker was started for us. *„kreni redom popravljaj testiraj radi sta vec treba
> da sve bude reseno."*

**What „executed rather than written" changed.** All seven migrations applied
cleanly to a real Supabase Postgres 17 on the first attempt, and the pgTAP suite
now runs — **75 assertions across four files, green**. Three findings came out
of running it that no amount of reading the SQL would have produced:

1. **`storage.objects` and `realtime.messages` cannot be FORCED, by anyone.**
   The migration attempted `alter table … force row level security` on both and
   downgraded a failure to a WARNING; its header guessed that „in most Supabase
   projects the migration role is a member of both". It is a member of neither,
   on every project there will ever be: those tables are owned by
   `supabase_storage_admin` / `supabase_realtime_admin`, `postgres` is not in
   those roles, and no hosted project issues those passwords. The wall was
   reported present and was not.
   **Fixed by changing the claim, not the test.** FORCE removes the *owner's*
   exemption; on `public`/`private` the owner is `postgres` — the migration
   role, the dashboard's role, whatever a leaked connection string grants — so
   there it is load-bearing. On these two the owner is a platform service role
   nothing Nexus can present is a member of. The assertion is now *FORCED, or
   owned by a role no Nexus identity can assume*, so if a platform change ever
   reassigns either table to `postgres` the gate goes red and FORCE becomes
   mandatory the same day. The `enable` and `force` statements were also split
   into separate blocks: one block would have rolled `enable` back when `force`
   threw, silently un-enabling RLS on the table holding every file byte.
2. **`anon` is refused before a policy is ever consulted.** The new
   `03_catalog_surface.test.sql` asserted „anon sees no rows" and got
   `permission denied for table sync_objects` instead — migration 002's
   `revoke all … from anon` means the request never reaches RLS. Asserting the
   stronger shape (`throws_ok` 42501) is the point: `is_empty` would still pass
   the day somebody re-granted `select` and left the wall to the policies.
3. **A gate nobody ran.** `supabase/` was not a pnpm workspace member, so its 33
   static tests and the `check-rls-wall.mjs` audit were invoked by nothing.
   Now a workspace package, with `check:rls` in `package.json` and a `database`
   job in CI that starts a real Postgres and runs the suite.

**The cloud-off boundary now exists, and it exists BEFORE the thing it guards.**
`apps/desktop/src/main/net/offline.ts` — four layers, not a boolean:
a `webRequest.onBeforeRequest` allowlist over schemes and origins, a proxy
pointed at a dead loopback port with loopback bypass disabled, `host-resolver-rules
MAP * ~NOTFOUND`, and the spellchecker off. The device switch is `cloud.json`
beside `accounts.json`, read fail-closed — missing, unparseable, `"true"`,
`1`, `{}` all read as OFF. `check:egress` is the style half (16 rules, each
with a test, comment-stripped so the gate no longer fires on the privacy copy
that describes it); the boundary and its 10 unit tests are the assertion half.
The dev server also has a CSP for the first time — `rendererHardening` is
`apply: "build"`, so `pnpm dev` had run with none, which is exactly why the
esm.sh font fallback the review found was live there and not in the packaged app.

**Two defects found in this work, by running it:**

- `setSpellCheckerDictionaryDownloadURL('')` — the review's own wording — is
  refused by Electron as an invalid URL, and refused by **rejecting a promise it
  creates internally** while the method itself returns `void`. There is nothing
  to `await`, nothing to `.catch()`, and a `try`/`catch` catches nothing; the
  rejection lands unhandled inside `app.whenReady()` and strands the rest of
  startup. Twice the smoke rehearsal sat with a window open at 0% CPU until it
  was killed. **The line was removed rather than repaired:** the spellchecker is
  already off for the session, off per-window in both `webPreferences` blocks,
  and any dictionary request is cancelled by layer 1 — a fourth layer that can
  take startup down is the control breaking the product it protects. It is also
  a reminder that a review recommendation is a claim like any other.
- `cloudRequiresRestart` returned `from && !to` and its comment claimed enabling
  cloud took effect immediately. False: the resolver block is installed at
  launch and is fixed for the process lifetime, so enabling mid-session would
  leave DNS dead while every setting read „on". Both directions need a restart.
  The test had been written to match the implementation and therefore agreed
  with the bug.

**`@nexus/sync-port` — the crypto is no longer hypothetical.** `port.ts`
specified two adapters that „MUST agree byte-for-byte"; that obligation is
discharged by removing it. WebCrypto covers everything but Argon2id and
`globalThis.crypto` is standard in Node 24, the renderer and the browser;
Argon2id is `hash-wasm`, the same WASM `@nexus/core`'s local key chain already
uses. **One implementation, so „the adapters agree" is true by construction.**
X25519 comes from WebCrypto with `extractable: false`, so the private scalar
never enters the JS heap, and low-order points are rejected by the platform —
verified against Node 24, then checked again in our own code because RFC 7748
makes the platform's check optional.
26 tests, every vector from OUTSIDE this repository: RFC 6234, RFC 4231,
RFC 5869, and two Argon2id vectors generated by the reference C implementation
in a throwaway container. The first draft pinned the wrong Argon2 figure from
memory (it was the Argon2**i** number) — caught by asking the reference
implementation instead of the test author.

**B8 closed — `parent_id` is now in the row AAD.** It was the one clear,
server-writable column left unauthenticated while `version` and `deleted` were
bound. An untrusted operator could reparent any object with one UPDATE, tag
intact, every client accepting it — moving a transaction under another account,
or sliding a live row beneath a tombstone for the cascade to reap. `null` and
`""` encode differently (a presence byte), so „this is a root" and „this hangs
off the empty id" cannot be swapped either.

**B10 closed — the attachment „open" path was a live RCE, in the shipped
build.** `openExternally` ends in `shell.openPath`, which on Windows is
ShellExecute: the OS decides what to RUN from the extension and from nothing
else. The name it was handed came from `sanitizeFileName(attachment.fileName)`,
and `fileName` is a renderer-supplied display string validated only as „a
non-empty string" — while `sanitizeFileName` deliberately *preserves* the final
extension so a user's `.pdf` still looks like one. A renderer with a scripting
foothold therefore attaches arbitrary bytes as `Ugovor.pdf.exe`, the user clicks
„otvori", and native code runs OUTSIDE the `sandbox: true` renderer, defeating
the control the whole Electron design leans on hardest — from inside the process
that control exists to contain.

The extension now comes from `sniffMime` over the bytes, which are already
decrypted and in hand at that moment, so there is nothing for the renderer to
influence and nothing stale (a `mime` column written at upload time could be
both). An unrecognised type yields NO extension, which makes Windows show its
„open with" chooser — a human deciding what opens bytes the product could not

#### THE MONEY DEFECT — every dinar figure was 100× too large in the shipped app

Found by disbelieving a subagent's report. It was asked to fix the demo's
absurd RSD amounts, came back with evidence that the SEEDER was correct, and was
right — which made the answer worse.

`currencyMinorDigits` asked
`Intl.NumberFormat(…).resolvedOptions().maximumFractionDigits` — a **display**
library — for a **storage** scale. Node's ICU answers RSD = 2. Chromium's
answers 0, because Serbia has written dinars without para for years and CLDR
records the custom. The vitest suite runs under Node, asserted 2, agreed with
ISO 4217, and passed; **the app runs under Electron, and rendered every dinar
amount a hundred times too large**, while a bank-statement CSV import parsed one
a hundred times too small.

The exponent of a currency is a property of the currency, fixed by ISO 4217 —
RSD has 100 para whether or not anyone spends them. It is now a stated table,
and `money.ts` passes the digits INTO `Intl` so the integer split and the
rendering are one decision rather than two that happened to agree. The
regression test pins the answer AGAINST the runtime's, so an implementation that
merely forwards ICU cannot satisfy it and the RSD assertion at once. **DC-10.**

#### The design direction, measured rather than asserted

A research pass ran APCA, WCAG and OKLab over the real token files. Three
findings were arithmetic, not opinion, and they explain „sirovo i nije
skenabilno" precisely:

1. **The ink ramp was missing its most-used tier.** Noć's `textMuted` sat at
   APCA **Lc 43** — below the readable-body floor — while `text` sat at Lc 93.
   A 50-Lc hole in the middle means every row in every list is either shouting
   or whispering, with nothing in between; scanning needs the intermediate tier
   and there wasn't one. There are now four: `text` / `textMuted` (secondary and
   genuinely readable) / `textSubtle` (tertiary, the old `textMuted` value) /
   `textFaint` (**not text** — marks only, and gated at 3:1 rather than 4.5:1).
2. **Dan's cards were invisible as objects.** `surface` on `bg` is ΔL\* 2.6 with
   `shadow: none`, so the only thing distinguishing a card from the page was a
   border at 1.36:1. Hairlines are now checked as a **band** (1.2–2.4:1): a
   floor produces a wireframe, and no floor produced this.
3. **Colour cannot carry fourteen identities here.** The eight accents measure
   out as three perceptual families with a **203° dead arc** where
   purple/blue/orange would be — `ruza` and `bordo` are 4° apart, `suma` and
   `zad` are 4° apart. So identity moved to GEOMETRY: the fourteen module marks
   the icon set already carries now appear at four scales — 16px in the title
   strip, 18px in the rail, 48px in an empty state, 72px as a watermark behind
   every page header. Nothing new was drawn for it.

#### A new gate: `check:tokens`

The canvas agent found `font-size: var(--nx-font-size-bodySm)` in the title
strip. There is no such token — the emitted name is kebab-case. **CSS drops an
undefined custom property silently**: the declaration vanishes, the element
keeps what it inherited, and the result is a size nobody chose that happens to
look plausible. It had shipped since the strip was written, with every gate
green.

That is the raw-colour gate's class one step further along: that gate proves a
colour COMES FROM the tokens, and nothing proved the token being asked for
EXISTS. `scripts/check-tokens.mjs` now walks every `var(--nx-*)` in the app and
package sources and refuses any that resolves to neither an emitted token nor a
declaration in the tree. Two patterns are excluded, both deliberately: a name
completed at runtime (`var(--nx-swatch-${accent})`) cannot be checked
statically, and a capture ending in „-" is a prefix rather than a name — a
placeholder or a `*` in a doc comment. Reporting either would make the gate cry
wolf, and a gate that cries wolf gets muted, which is DC-01 exactly.

Watched failing first, on the real defect, before being wired in.

**ORDERING STOPPED BEING A NUMBER (2026-08-08, late).** ADR-082 mapped what
syncs and as what, across all 71 tables, and its first finding was not about
sync at all: the sparse-integer sort key every drag-to-reorder has written
since migration 022 cannot be merged between two devices, because the recovery
when a gap runs out is a mass UPDATE of the whole scope and a merge cannot tell
that apart from a deliberate reordering. Schema 62 replaces it with a
fractional rank, which has no gap to exhaust — so a move writes exactly the row
that moved. Done BEFORE the first row ever syncs, because afterwards it is a
migration of every task on every device. Full entry in §3.

**Eight primitives, and the vocabulary is closed.** `ChartFrame`, `CellMatrix`,
`ProportionBar`, `ColumnPlot`, `SeriesPlot`, `SpanLanes`, `RadialCycle`,
`ChartLegend`, over `@nexus/core`'s `charts/geometry.ts`. Forty-nine candidate
graphics across ten modules reduced to eight shapes by one rule — a primitive
must serve three modules, and anything narrower stays its own module's
component. What matters is not what they draw but **what they cannot say**:
- `ChartFrame` makes three house rules unbreakable rather than written down. A
  chart with nothing to say is ABSENT, not empty (`empty` carries the SENTENCE
  saying why, so no call site can render an axis with no data on it);
  `description` has no default, so a chart nobody can describe does not
  compile; and the sentence is composed by the same derivation that produced
  the drawing, so it cannot drift into a fabricated statistic wearing an
  accessibility badge.
- `CellMatrix`'s `cellAt` returns `null` for NOT DRAWN and `level: 0` for a
  MEASURED ZERO. Painting silence as zero is the commonest lie a heatmap
  tells, and here it is unrepresentable.
- `ColumnPlot` and `SeriesPlot` are deliberately NOT one configurable chart. A
  banded domain says absence is a missing slot; a continuous one says absence
  is a break in the line. Merged behind one `marks: []` array, somebody
  eventually feeds gappy daily numbers to a line and gets an interpolation
  claiming a measurement that never happened.
- `ColumnPlot` grew `layout="grouped"` the first time two non-additive series
  met a band. Stacking states that the series ADD UP: twenty tasks created
  stacked on twenty closed would tower over a dead week with a total that does
  not exist.

**WAVE 54 — „Merenja" and „Napredak": FIT closes, and every number on it says
where it came from (2026-08-07).** Slice d of ADR-081, and the end of the arc.

**THE PROGRESSION ARITHMETIC IS `@nexus/core`'s and stores nothing.** There is
no personal-record table and there will not be one: a PR row and a set table
can disagree, and only one of them is the truth. `progress.ts` derives records,
weekly volume and the estimated-1RM trend from the sets on every read, and
every one of them is a refusal as much as a calculation:
- **„The heaviest assisted pull-up" is the one figure it will not print.**
  There a bigger number is LESS work, so the record that applies is the least
  help you needed — which is `assisted_reps` earning its place as a metric of
  its own, three slices after the decision was made.
- **A weighted pull-up gets no estimated 1RM.** The belt is not the load, the
  body is, and this module does not know what the body weighs.
- **Hard sets and tonnage are never conflated.** Hard sets per muscle group is
  what a week is balanced against; tonnage means something for the strength
  lifts and nothing for a plank. A set counts one toward each PRIMARY muscle and
  nothing toward its secondaries — counting secondaries would bill one bench
  press to chest, triceps and front delts and make every total read about twice
  the training that happened.
- **No calorie burn**, said out loud on the page rather than left as a gap.

**„MERENJA" IS THE THIRD SECTION, and it is where an app is most tempted to
invent.** The figure and the line are both a 7-day moving average with the raw
readings drawn behind them; a change is reported between two AVERAGES over
roughly thirty days (`trendChange`, new in core), never yesterday against
today. Nexus computes no body-fat percentage — the field takes what the user's
caliper or scale reported — and BMI is drawn ONLY while there is no body-fat
reading, labelled as the population screening figure it is.

**The three energy tiers ship with the sentence ADR-081 §8a calls the
feature.** The page names the tier that produced the number, lists what it
rests on, and says what would reach the tier above („izmeri procenat masti",
„beleži obroke češće"). The measured tier needed the one channel FIT was
missing: `fit:day-totals-range`, one total per logged day, because fourteen
round trips carrying every logged item to add up four numbers a day would be
the N+1 the module already refuses elsewhere — and because „nisam jeo" and
„nisam upisao" have to stay tellable apart for the 80 % coverage refusal to
mean anything.

**The calorie suggestion is offered and never applied.** There is no default
weekly rate anywhere: „pola kile nedeljno" is a recommendation and this app
makes none, so the field starts empty and the suggestion appears only once the
user has said how fast. Adopting it writes `fit_targets.kcal` and leaves the
other three goals untouched.

**The dashboard card reports a fact, not a plan.** „Trening" shows this week's
sessions and the routine that has gone longest without being done, with the day
it was last done beside it — never „na redu", because a routine holds nothing
about when and the card is not allowed to invent a schedule the module
deliberately does not have.
