# ADR-005 — Zero-Knowledge Crypto for Private Notes

**Status:** accepted (draft pending founder sign-off) · 2026-07-05
**Drives:** PRIV PRD (all), decision #6 (Recovery Kit default + informed
opt-out), decision #11 (web parity with caveat, auto-lock 5/2 min, 100 MB
cap); SEC-ZK-01..06, SEC-CR-01/03/04.

## Context

Private notes must be unreadable by server, admin, and backup operator —
including during sync (SEC-ZK-01). Crypto-UX research (2026-07-04) settled
the recovery model (Proton-style account/data recovery split, Recovery Kit
verified-save) and flagged the two hard constraints: WebCrypto has no
Argon2, and web-served code is a weaker trust anchor than installed apps.

## Options considered

- **Crypto library:** libsodium (audited, one opinionated API across
  Electron/web/RN via `libsodium-wrappers`' WASM build) vs WebCrypto +
  argon2 WASM add-on (two libraries, AES-GCM nonce discipline on us) vs
  Rust core via WASM/uniffi (best future cross-platform story, highest
  build complexity now). libsodium wins on audit surface and single-API
  simplicity; the Rust option is the designated Android/perf escape hatch.
- **KDF:** Argon2id (baseline-mandated, SEC-CR) — parameters tuned per
  device class (desktop higher memory cost than low-end Android later).
- **AEAD:** XChaCha20-Poly1305 (192-bit nonces make random-nonce misuse a
  non-issue; constant-time in software — no AES-NI dependency on old
  hardware) over AES-256-GCM.

## Decision

**libsodium end-to-end; envelope encryption with a passphrase KEK and a
Recovery Kit KEK; everything leaves the device as ciphertext only.**

- **Key hierarchy:** random 256-bit **DEK** encrypts all PRIV content
  (notes, attachments, the PRIV search index's persisted form). The DEK is
  wrapped twice: by **KEK_pass** = Argon2id(private-notes passphrase,
  per-user salt), and by **KEK_kit** = the Recovery Kit key (random,
  Base32-grouped, generated by default at PRIV setup; user must
  verified-save it or explicitly accept the risk — decision #6,
  SEC-ZK-04). Server stores only wrapped DEKs, salts, and parameters —
  never any KEK material (SEC-ZK-01/03).
- **Per-item encryption:** each note/attachment encrypted with
  XChaCha20-Poly1305 under keys derived from the DEK (HKDF, per-item
  context), random nonces, AAD binding item-id + version to prevent
  swap/rollback splicing (SEC-CR-04).
- **Recovery semantics (the founder-signed trade-off):** account password
  reset restores the *account*, never PRIV. Passphrase forgotten →
  Recovery Kit restores PRIV. Both lost → **data is unrecoverable, by
  design**; the UI says so at setup and at every recovery touchpoint
  (crypto-ux research; SEC-ZK-04).
- **Unlock/session:** unlocked DEK lives only in memory; auto-lock 5 min
  desktop / 2 min web (adjustable — decision #11), on suspend, and on app
  quit. PRIV search runs on an in-memory index built at unlock
  (SEC-ZK-05); notifications carry no PRIV content (SEC-ZK-06).
- **Sync:** ciphertext blobs with version metadata (ADR-002); conflict =
  keep both copies. 100 MB per-attachment cap v1 (decision #11; premium
  1 GB+ later — streaming chunked encryption is the upgrade path,
  secretstream API).
- **Web caveat (decision #11: ship on web):** strict CSP, SRI on all
  bundles, no third-party scripts on app origin; the caveat — a compromised
  server could serve malicious JS to capture a passphrase — is documented
  in-product (crypto-ux research wording). Desktop remains the recommended
  home for PRIV; signed-bundle hardening is a future extension.

## Consequences

- Zero-knowledge is real: support cannot recover data — support docs and
  onboarding must keep saying it (already in PRIV PRD acceptance).
- WASM libsodium adds ~300 KB to web/desktop bundles — lazy-loaded with
  the PRIV module.
- The crypto package ships known-answer tests and round-trip property
  tests in CI (SEC-VER-02); any parameter change requires a versioned
  wrapped-DEK migration path (parameters stored beside the salt).
- 2SKD (device-secret hardening) stays parked post-v1 (crypto-ux research
  §8) — the key hierarchy already accommodates a third wrap.
