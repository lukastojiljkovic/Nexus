# Nexus E2EE sync — hardening specification

**Date:** 2026-08-08 · **Status:** the blockers B1–B10 are worked in
[../STATUS.md](../STATUS.md) and [../log/2026-08.md](../log/2026-08.md); this is
the specification they are worked against. Binding alongside
[baseline.md](baseline.md).

*Produced by a 13-agent red-team pass over the sync design — 42 attacks survived
triage across six lenses, every source claim read and every external claim
checked at the time of writing. It was committed as the raw JSON transcript the
run emitted, which meant a `.md` file that rendered as one escaped blob; this
is the same specification, unwrapped, byte-for-byte from that transcript's
`result.spec`.*

**Four claims this rests on, each checked on the day:** Electron 42 support ends
**2026-10-20**; Supabase's aal2-restrictive-RLS is the documented
MFA-enforcement mechanism; the built-in email cap is 2/hour project-wide; and
electron-updater's signature check is a `publisherName` string-compare that
no-ops when the field is absent — which it is in the shipped `app-update.yml`.

---

Scope note: `packages/sync` and `apps/desktop/src/main/net/` do not exist yet, so most of this is a constraint on code not yet written — cheap now, a rewrite later. The desktop findings (updater, shell, spellcheck, Electron EOL) are against shipped 1.0.0 and are live today. Every source claim below was read; every external claim was checked this session.

The whole review collapses to one root cause repeated from six directions: **the design hands the account-root key (MK) and the release decision to the lowest-assurance surfaces** — the browser, the pairing channel, the email-derived KDF, the un-MFA'd session, the unsigned updater. The fix is always the same shape: *give the weak surface less, and move the trust decision to the device that holds the secret.*

## 1. BLOCKERS — must land before any sync code ships (ranked by severity)

**B1. Disarm the auto-updater now; it is unsigned silent RCE and sync multiplies its payout. [24/32/33/35]**
`checkForUpdates()` (index.ts:11969-11980) runs `checkForUpdatesAndNotify()` with `autoDownload`/`autoInstallOnAppQuit` at their `true` defaults; `electron-builder.yml:36-59` sets no signing config, so `app-update.yml` carries no `publisherName`, and electron-updater's `verifySignature` returns `null` (= "verified") when `publisherName` is absent — a documented no-op ([Doyensec](https://blog.doyensec.com/2020/02/24/electron-updater-update-signature-bypass.html), [Snyk SNYK-JS-ELECTRONUPDATER-567704](https://security.snyk.io/vuln/SNYK-JS-ELECTRONUPDATER-567704)). Whoever controls the `lukastojiljkovic` account (or a TLS-MITM today) installs native code at next app quit with no click and no UAC. Post-sync that yields DK, the DPAPI device secret, MK, every CK_p and the stored Supabase refresh token — which survives wiping the machine.
- **Change:** gate index.ts:12151 behind a build-time constant `false` in shipped builds so 1.0.0 carries no armed updater against an empty feed. Before the feed goes live: `autoDownload=false`, `autoInstallOnAppQuit=false`, `disableWebInstaller=true`, handle `update-available` to prompt; Authenticode-sign the build and set `win.publisherName`; and publish a **detached Ed25519 signature over `latest.yml` verified against a public key compiled into the binary** before `quitAndInstall`. Signing alone is insufficient — it defends TLS and the GitHub account, not a compromised release token; the pinned Ed25519 key is what survives both.

**B2. MK must never enter a browser, and pairing must be confirmed on the device that holds MK. [1/25/28/31/36]**
The design gives the browser the account root and puts the one human trust decision (SAS) on W — the attacker's surface in every browser-threat variant: a phishing page the victim types their real code into [1], a backdoored bundle the origin itself serves (SRI/same-origin-manifest cannot detect this — [MDN SRI](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity), [Meta Code Verify](https://engineering.fb.com/2022/03/10/security/code-verify/)) [25], a malicious extension whose content script is not bound by page CSP and reads the "display-only" code off the DOM [31], or a compromised desktop renderer that simply never draws the SAS [36]. In all four, m4 ships `AEAD_{K_sess}(MK)` to the attacker; the outcome is durable (needs MK+CK_p rotation). `assertTrustedSender` (index.ts:1444-1448) proves *which window* sent an IPC, never *that a human asked*.
- **Change (three parts, all required):**
  1. **Scope keys down.** The browser session receives only the CK_p of profiles explicitly marked web-enabled, delivered wrapped under a per-session key; **MK stays desktop-only**. A backdoored bundle then costs one profile's content key (rotatable) instead of the account root and every future write. A per-profile `cloud: never` flag enforced by *never wrapping that CK_p under MK* makes "poslovni profil je samo na računaru" a cryptographic fact, not a UI toggle.
  2. **Move consent into desktop main.** Before D emits m4, in the main process (renderer cannot forge or suppress it): show the peer's `device_name` and the **server-attested account email** in a `dialog.showMessageBox` (already imported, index.ts:13), require the account passcode through the existing `verifyPasscode`/`handleProfilesVerifySwitch` throttle (index.ts:1406), and raise a `Notification` on every completed pairing. D pins the expected email (the one linked when sync was enabled) and refuses on mismatch. This turns the human check from "do two numbers match" (which a genuine wrong endpoint also passes) into "is this MY account receiving my key" (which a phisher fails).
  3. **Reverse the code direction.** Generate the 13-char code on the desktop (the MK holder), typed into a browser already logged into the account — strictly safer, per the pairing lens.

**B3. One `RESTRICTIVE` aal2-or-live-device RLS policy per table, and a non-persistent web session. [14/19/22/37]**
Every stated policy is `user_id = auth.uid()`, which is satisfied at aal1 — so the founder's accepted residual ("whoever has the password *and defeats MFA*") is false: there is nothing to defeat, and a password-only session reads and writes everything ([Supabase MFA-via-RLS](https://supabase.com/blog/mfa-auth-via-rls), [auth-mfa docs](https://supabase.com/docs/guides/auth/auth-mfa)). Permissive policies OR together, so the gate must be `AS RESTRICTIVE`. Two corrections make this correct: the desktop's pair-minted session is aal1 forever, so a blanket aal2 gate locks the desktop out — the predicate must be **aal2 OR a live registered-device session**; and the pairing INSERT itself must be aal2-only, or a password-only session mints its own device and sails past the gate.
- **Change:** one policy per exposed table (`sync_objects`, `key_wraps`, `devices`, `pairing`, `sync_state`), on `storage.objects` and `realtime.messages`:
  `AS RESTRICTIVE TO authenticated USING ((select auth.jwt()->>'aal') = 'aal2' OR exists (select 1 from devices d where d.session_id = ((select auth.jwt())->>'session_id')::uuid and d.revoked_at is null))`.
  Require an enrolled+verified TOTP factor **before MK is first wrapped under K_wrap**. Store the JWT `session_id` in `devices.session_id` so this same policy is the instant kill-switch (B-cluster with revocation below). **This policy does not protect a stolen refresh token** — `aal` survives refresh, so a token lifted from localStorage refreshes back to aal2 [22]. Therefore construct the web client `persistSession:false`, in-memory storage, `flowType:'pkce'` (moves recovery/magic-link tokens off the URL fragment); if "stay signed in" is wanted, hold the refresh token in a `__Host-`, HttpOnly, SameSite=Strict cookie via the Cloudflare Worker as a BFF, never in the page.

**B4. A `BEFORE UPDATE` trigger on `sync_objects`; RLS cannot see OLD and an aal1 session is otherwise a permanent-lockout primitive. [18]**
Postgres `WITH CHECK` sees only NEW, so RLS structurally cannot enforce version monotonicity, tombstone terminality, or column immutability. The sharpest attack in the review: set `version = 9223372036854775807` with garbage ciphertext on every row. AEAD does not help (honest clients cannot decrypt it and cannot write past a version that has no successor), there is no delete policy by design, and the design's own anti-rollback high-water mark *latches the poisoned counter into every device permanently*. A newly paired device, having no mark, seeds the poison as truth.
- **Change:** `BEFORE UPDATE` trigger enforcing `NEW.version = OLD.version + 1`, `OLD.deleted = false` (tombstones terminal), immutability of `user_id/profile_id/collection/object_id`, and `updated_at = now()` from the server clock. Tombstones carry `AEAD(∅, aad)` so a client applies a deletion only on a verified tag, never on the clear `deleted` column. Fresh devices seed high-water marks from the paired desktop over the K_sess channel (extend m4), not from the server.

**B5. The server MK-wrap needs its own KDF profile and a Vault-held pepper; a Postgres dump is otherwise a complete offline attack on every user. [8/15/37/42]**
`salt = SHA-256("nexus/web-kdf/v1" ‖ lowercase(email))` is reconstructible from the email that sits in the same dump, so an attacker precomputes a targeted table *before any breach* and the dump only supplies the AES-GCM tag to test against. The design gives this "travels anywhere, offline-attackable forever" wrap the local hot-path profile (64 MiB/t=3, keyChain.ts:33-39) while the codebase's own archive profile for exactly this case is 128 MiB/t=4 with the written rule that the work factor is "the only defence standing between the file and its contents" (keyChain.ts:41-58). MFA is an auth-layer control the offline attack never touches — stop listing it as an at-rest mitigation.
- **Change:** (1) server wrap gets ≥256 MiB/t=4/p=1, params recorded in the `key_wraps` row as keyChain.ts already does locally; (2) mix a 32-byte per-user pepper **into K_wrap only** (`K_wrap' = HKDF(K_wrap, salt=pepper)`) — K_auth must stay derivable pre-auth — held in [Supabase Vault](https://supabase.com/docs/guides/database/vault) and returned only by a `SECURITY DEFINER … SET search_path=''` function behind an aal2 Edge call, so a `pg_dump`/PITR/backup exfil is uncrackable; (3) since GoTrue now only ever sees the 256-bit K_auth (bcrypt of which is uncrackable and a legitimate use), enforce the human-password floor **client-side** — zxcvbn ≥ 4 / ≥ 60 bits and the HIBP k-anonymity range check — as a load-bearing control, not advice. Availability cost, stated plainly: lose the Vault secret and the password path to MK is dead; SRC or a paired desktop recover it.

**B6. Decouple the KDF salt from GoTrue's mutable identity, and own the reset/email-change ceremonies. [6/7/13]**
Three findings share one class: encryption-key derivation is bound to GoTrue's self-service identity surface with no Nexus ceremony between them. Supabase `updateUser({email})` is supported self-service ([docs](https://supabase.com/docs/reference/javascript/auth-updateuser)); after old→new email the next login derives K_auth' and K_wrap' from a new salt — login fails against `bcrypt(K_auth_old)` and K_wrap' cannot open the still-old-wrapped MK. The stock GoTrue recovery page stores `bcrypt(P)` of whatever the user types, but login sends `K_auth = Argon2id(P, salt)`, so **the native reset locks the user out of auth on the exact path a user in trouble reaches** — the design's "reset restores authentication only" is false as specified.
- **Change:** mint a random 128-bit per-account salt server-side, fetch at login, derive K_auth/K_wrap from it — email change and canonicalization (case/plus-addressing/IDN) become crypto-irrelevant. This must be right before the first K_wrap; you cannot re-salt later without re-wrapping everyone. Own the reset UI reached from the recovery link (`updateUser({password: K_auth'})`), never expose GoTrue's default page, and state that a reset restores auth but not MK (obtain MK from SRC or a paired desktop). Pin K_auth's wire encoding to lowercase-hex-64 (comfortably under bcrypt's 72-byte truncation, [confirmed](https://github.com/orgs/supabase/discussions/34207)) with a cross-client test vector.

**B7. `pair-complete` must consume the token in one atomic SQL statement; the TTL/single-use invariant currently lives only where the redemption path bypasses it. [3/16]**
Edge Functions run with the secret key that bypasses RLS ([function secrets](https://supabase.com/docs/guides/functions/secrets), [API keys](https://supabase.com/docs/guides/getting-started/api-keys)), so the `expires_at > now()` predicate "inside the policy" never runs on redemption. If single-use is a JS read-then-write it is a TOCTOU that mints two sessions from one token. A leaked token (function logs, gateway query strings) then becomes persistent account takeover — worse than a one-shot MK theft, and the downstream amplifier of a B2/SAS MitM that captured K_sess.
- **Change:** `update pairing set consumed_at = now() where rendezvous_id = $1 and token_hash = sha256($2) and consumed_at is null and expires_at > now() returning user_id;` — mint only if exactly one row returns, take identity **from the returned row, never from a caller-supplied email/user_id** (the [CVE-2025-48370](https://advisories.gitlab.com/pkg/npm/@supabase/auth-js/CVE-2025-48370/) lesson: never pass a client string to `auth.admin.*`). Constant-time hash compare is subsumed by the SQL equality. Token in the body only, `Cache-Control: no-store`, no `console.log` of the request; bind redemption to a K_sess MAC over `epk_D‖rendezvous_id` as defense-in-depth. Set email-OTP expiry ≤ 300 s.

**B8. Freeze the crypto envelope before the first ciphertext exists. [39/40/42/11/13]**
These are individually lower-severity but share one property: **none can be changed after rows exist without re-encrypting the corpus**, so they must be correct on day one.
- `parent_id` is a clear, server-writable column excluded from the row AAD while every other acted-upon clear column (`version`, `deleted`) is bound [39]. An untrusted operator rewrites `parent_id` with one UPDATE; the tag is untouched, every client accepts the new parent — silent key-free reparenting (move a transaction to the wrong account, cascade-delete live rows under a tombstone). **Add `parent_id` to the AAD and carry the authoritative parent inside the ciphertext; treat the column as a hint no tree/GC path trusts.**
- Pin the nonce spec: fresh random 96-bit per seal (matching privEnvelope.ts/blobCrypto.ts/keyChain.ts:206), **never a counter** (two uncoordinated devices on the shared CK_p collide near zero → key-nonce reuse → GHASH forgery), distinct nonces for pairing m1 vs m2, with a documented per-CK_p seal ceiling well under 2³² and an auto-rekey trip [40].
- Key-commit every MK/CK_p wrap: AES-GCM is not committing, enabling a partitioning oracle on the low-entropy K_wrap and cross-key confusion [42]. Store `HMAC-SHA256(wrapKey, context-label)` beside each wrap and verify before trusting it (extend keyChain.ts:205-235).
- Bind `{user_id, type, wrap_version, algorithm, kdf_params}` into each wrap's AAD with monotonic `wrap_version`, and reject any wrap below a client-side Argon2 floor so a hostile server cannot replay a superseded or weak-param wrap [11].

**B9. Make MK minting an atomic singleton. [9]**
"First device to enable sync" is a check-then-act with no compare-and-set; two concurrent enables (desktop + web tab, retry after network flap) each mint a distinct MK and CK_p-wrapped-under-its-own-MK, and RLS permits both inserts. Result: rows silently undecryptable across devices, two ambiguous SRCs.
- **Change:** a `key_wraps type='master'` row with a UNIQUE constraint, or an Edge `INSERT … ON CONFLICT DO NOTHING RETURNING` the winner; the loser adopts the existing MK and deletes its provisional material.

**B10. Attachment temp-file extension must come from the main-sniffed mime, not the renderer name. [34]**
Live today: `attachNoteFile` (preload:433) takes a renderer name validated only by `asNonEmptyString`; `openExternally` (attachments.ts:223-241) writes `join(tempDir, sanitizeFileName(fileName))` and calls `shell.openPath` — ShellExecute. `sanitizeFileName` (attachments.ts:187-212) explicitly preserves the final extension, so a renderer with a scripting foothold attaches bytes as `Ugovor.pdf.exe` and executes native code outside the `sandbox:true` renderer — nullifying the control the design leans on hardest, and sync only widens the renderer surface.
- **Change:** in `openExternally`, derive the extension from the stored main-sniffed `mime` (index.ts:8783, which the renderer cannot forge) and ignore the display name's extension; an `application/octet-stream` sniff yields no extension so Windows shows its "open with" chooser. When sync ingestion is built, re-download, verify the claimed sha256, and re-sniff received bytes — `assertTrustedSender` gates the renderer; the network needs its own gate.

**B11 (conditional — if Storage ships in slice 1). Storage bucket must be private. [23]** A public bucket makes SELECT policies moot and silently undoes the HMAC object names. Assert `storage.buckets.public = false` in CI.

**B12 (dated blocker — 2026-10-20). Be off Electron 42 before EOL. [38]** [endoflife.date](https://endoflife.date/electron) confirms Electron 42 support ends 2026-10-20 — 73 days out — the day 45 goes stable and the three-version window closes. After that, zero Chromium security backports, while the app grows its first network surface. Remove the pin's *cause*: build `better-sqlite3-multiple-ciphers` from source in CI against the target Electron ABI with `@electron/rebuild` and cache it, so the app tracks Electron instead of the upstream prebuild calendar.

## 2. REQUIRED — before the feature is "done" (first slice survives without them)

- **Per-device Ed25519 write signing + an MK-signed device roster. [10]** Sync rows are authenticated only by the shared CK_p, so any CK_p holder forges rows every honest device accepts (LWW overwrites, tombstone flips, poisoned Yjs). This is the direct consequence of "no asymmetric keys in v1" and is currently an *accident*, not a signed-off decision. Mint an Ed25519 keypair at pairing, publish public keys in an MK-signed roster, sign every row over `(AAD ‖ ciphertext)`, reject unknown/evicted authors — this also makes revocation partly cryptographic. Until it lands, record write-integrity loss in the residual list explicitly.
- **Set-level anti-rollback anchor + Yjs freshness. [30a/40/41]** AAD binds each row to its own identity, never the *set* — a malicious server serves an older internally-consistent snapshot or omits rows and every open succeeds. Put `(max_version_per_collection, row_count, monotonic_counter, client_time)` in `sync_state` **MAC'd under an MK-derived key the server does not hold**; refuse any response whose counter regresses (hard stop, visible warning, never silent resync). Each compacted Yjs snapshot's plaintext commits (hash-chain / state-vector) to exactly the updates it subsumes; a client treats a note as current only if it can assemble a contiguous update set anchored to the newest snapshot it has seen.
- **Instant, bounded revocation. [19/23]** Set project JWT expiry to 300 s (bounds every stateless-token gap at 5 min, [sessions](https://supabase.com/docs/guides/auth/sessions)); the `devices.session_id` restrictive policy (B3) is the data-path kill switch; force a Realtime disconnect on revoke via a control-channel write (join-time policy cache otherwise persists for the JWT lifetime, [realtime authz](https://supabase.com/docs/guides/realtime/authorization)); cap Storage signed-URL TTL at ≤ 300 s — a signed URL is a bearer token that ignores RLS and revocation for its whole life.
- **Edge Function blast-radius control. [16/17]** Scoped `NOINHERIT, NOBYPASSRLS` roles per function (contains an SQL-shaped bug, *not* RCE — the injected secret key is still in `Deno.env`, so a fully compromised function is total; say so honestly); committed `deno.lock`, deploy `--frozen`, zero unpinned `https://` specifiers; rotate to `sb_secret_*` keys (legacy `service_role` JWTs can't be revoked without a project-wide JWT-secret rotation that signs out every user); keep the function count minimal; treat any function compromise as full-DB in the incident plan.
- **Supabase platform. [20/21]** Custom SMTP from day one (the [2-emails/hour built-in cap is project-wide](https://supabase.com/docs/guides/auth/rate-limits) — one attacker denies recovery to every user); front `auth.*` on the Worker with Turnstile + a Workers-KV per-email token bucket; enable Secure Password Change (reauthentication nonce); set a Spend Cap. Tombstone GC as `SECURITY DEFINER … SET search_path=''` with the 90-day floor and mark-monotonicity enforced *server-side* (a `sync_state` increase-only trigger — the marks are client-writable, so a session that sets them to MAX forces early GC and resurrects deleted objects). Never write a policy against `auth.jwt()->'user_metadata'` (user-editable; Supabase rates it ERROR 0015) — `profile_id` scoping comes from a server-side table.
- **Storage lifecycle. [23]** Carve Storage out of the no-delete rule: deleting an attachment is a real DELETE, not a tombstone (tombstoning the user's own blob is a privacy-promise failure and a storage cost). Four owner-prefix policies — select/insert/update **and delete** — since upsert silently needs SELECT+UPDATE.
- **IndexedDB is per-origin, not per-user. [30b]** Name the DB `nexus-<user_id>`, `indexedDB.deleteDatabase()` on sign-out/expiry, and offer a "ovo nije moj uređaj" in-memory-only mode — otherwise two accounts on a shared browser profile see each other's cleartext metadata (the set the founder accepted the *server* seeing, not the next person at the laptop).
- **Turn "cloud off" into a real boundary. [29/33/35]** The grep gate and Node tripwire are honesty checks, not boundaries — dev already makes a live esm.sh font fetch (excalidrawAssets.ts) and the shipped app fetches a Google spellcheck dictionary (`spellcheck` defaults true; only two inputs opt out), contradicting the "Jedino… provera verzije" privacy copy (strings.sr.ts:6760). With cloud off, install `session.defaultSession.webRequest.onBeforeRequest` cancelling any scheme not in an allowlist (`file`, `devtools`, `nx-blob`, `priv-blob`, dev-server origin), `setProxy` to a dead loopback, and `host-resolver-rules=MAP * ~NOTFOUND` (blocks DNS but not literal IPs, so keep the Node shims — add `node:child_process/http2/dgram`). Set `spellcheck:false` on both windows plus `setSpellCheckerDictionaryDownloadURL('')`. Run the off-mode test against the **packaged** app under a Windows Firewall block-and-log rule scoped to `Nexus.exe`, failing on any logged packet — not on an uncalled JS symbol. Add `font-src 'self' data:` to the dev server's headers.
- **CSP as declared + reporting. [27]** `connect-src 'self' https://<project>.supabase.co wss://<project>.supabase.co` and add `report-to` with a collector — the stated policy has no reporting directive, so a partial bypass is silent. State in writing that CSP prevents script *execution*; everything after (DNS-prefetch and script-navigation exfil are ungoverned by any CSP directive) is bounded by non-extractable keys (B2), not a header. Keep `'wasm-unsafe-eval'` (required by hash-wasm, does not permit JS eval); do **not** add COEP (would enable Spectre reads of the worker heap).
- **Cipher choice for the multi-writer surface. [crypto]** Prefer XChaCha20-Poly1305 via `@noble/ciphers` (192-bit random nonce ends the collision problem across the fleet and every bulk re-encrypt) or XAES-256-GCM if AES-NI throughput is mandatory; keep the single-writer local at-rest code on WebCrypto AES-GCM. Raw random-96-bit GCM is acceptable *only* with the B8 ceiling enforced. Add a baseline rule: never compress plaintext before encryption on any path mixing attacker-influenceable and secret content (CRIME).
- **Supply chain. [26]** Pin all `uses:` in `ci.yml`/`security.yml` to full 40-char SHAs (tag as comment; Dependabot maintains SHA pins) — [tj-actions/changed-files CVE-2025-30066](https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066) repointed every tag to one malicious commit. This becomes a **blocker** the moment `CLOUDFLARE_API_TOKEN` lands: put the deploy in a separate workflow, `permissions:{}` at top, bound to a protected `environment:` with required reviewers, no third-party actions. Also re-derive the `nanoid`/`mermaid` override list so `pnpm audit --prod` goes green — a red gate is a rumour (DC-07). Do not ship CANV to the web (18 MB of Excalidraw + the esm.sh fallback is the single largest available browser attack-surface cut).
- **Pairing details. [5/pairing-note]** Pin pairing Argon2id to ≥64 MiB/t=3; generate the 13-char code via the rejection-sampled 5-bit-window encoder in `recoveryCode.ts:44-57` for a true ~65 bits with no modulo bias; treat `device_name` as untrusted (escape, length-cap, label "claimed name", never let it imply verification — the human decision rests on the attested email); enforce a tight wall-clock deadline on the whole m1..m4 exchange (delay is what gives a SAS-grinder time); consume the code on any abort/timeout so a code-knower cannot resume a half-open session.
- **Password change is not remediation. [12]** When initiated as a compromise response, force/steer to MK+CK_p rotation and re-encryption, and state that a bare re-wrap neither re-protects synced data nor revokes what an attacker already pulled.

## 3. DESIGN AMENDMENTS — where the design was wrong, not merely unfinished

1. **SAS confirmation direction reversed.** *Was:* code minted in the browser, "confirm ON W." *Now:* code minted on the desktop, confirmed on the desktop against a server-attested account email. A SAS authenticates the channel; it cannot authenticate the account, and putting it on the attacker's surface makes it decorative. [1/36]
2. **MK is desktop-only; the browser gets per-profile CK_p.** *Was:* MK wrapped under a web-password key, browser holds the account root. *Now:* the browser never holds MK; web-enabled profiles' CK_p only, wrapped per-session, non-extractable. Device enrolment (which needs MK) is a desktop-only operation. [25/28/31]
3. **Add a commitment round to the handshake (ZRTP `hvi`).** *Was:* two-move reveal (m1 exposes epk_D, m2 exposes epk_W) with no prior commitment — a code-knowing on-path attacker grinds the 6-digit SAS to a certain collision in seconds, inside the TTL. *Now:* the first mover sends `H(epk)` and reveals `epk` only after the peer commits; the SAS binds both commitments. This is what makes 6 digits sound; PAKE does not help (it only proves both know the code, which the phisher does). [2]
4. **Random per-account server-held salt replaces the email-derived salt.** [6]
5. **Nexus-owned reset and email-change ceremonies replace GoTrue's native pages.** [7]
6. **Add per-device Ed25519 signing** — the "no asymmetric keys in v1" decision was wrong for write integrity. [10]
7. **Revocation moves from auth-layer to the data path** — `delete devices row + admin-revoke` lags a full token lifetime; the `devices.session_id` restrictive predicate + 300 s JWT + forced Realtime disconnect make it near-instant. [19]
8. **Storage is exempt from the no-delete rule** — tombstoning converges sync rows; it strands the user's own encrypted blob. [23]
9. **"Cloud off" is a network boundary (webRequest allowlist + proxy + host-resolver), not a grep** — the grep and tripwire stay as style checks, but the guarantee is asserted at the packet layer. [29]

## 4. GATES — in the spirit of `check:colours`/`check:tokens` (scoped, precise, self-tested, CI-wired)

- **`check:rls`** — extend the planned two-JWT test into a catalog+behaviour assertion, run against a real Postgres in CI: (a) an **aal1** JWT and the **anon** role each get zero rows from every exposed table (the planned two-user test uses two aal2 users and cannot see either gap); (b) a device-session JWT gets only its owner's; (c) zero relations of `relkind in ('v','m','f')` in exposed schemas outside an allowlist, and allowlisted views carry `reloptions @> '{security_invoker=true}'`; (d) zero `prosecdef` routines outside an allowlist, allowlisted ones pin `search_path`; (e) `execute` revoked from anon/authenticated on non-exposed functions and `usage` revoked on schema `graphql`; (f) every `storage.buckets.public = false`. ## 5. RESIDUAL RISKS — what remains after all of the above, stated plainly

- **Metadata in the clear (accepted).** Add to the ledger: `updated_at` + per-collection row counts reconstruct a user's daily rhythm, and no AAD can hide it. Correct RLS means there is no metadata-extraction path for an *outsider*; the exposure is to Supabase-the-operator and to legal compulsion.
- **The web password is an offline oracle bounded by KDF+pepper+strength (accepted, sharpened).** With the Vault pepper, a *database-only* dump is uncrackable. Not covered: an *app-tier* compromise (Vault + the pepper function together) re-exposes the offline grind, and a user who insists on a weak password is weak against that narrower attacker. Restate honestly: at-rest confidentiality under app-tier compromise equals password-guessing hardness; MFA is not part of that calculus.
- **Browser-delivered E2EE is structurally weaker than desktop (new residual — write it down).** A backdoored bundle, an XSS, or a malicious extension on a web-enabled profile yields that profile's CK_p for the session and B4's writes — reduced from the account root and every future write, but not eliminable origin-side (SRI and same-origin manifests cannot detect the host serving the document; the only deployed answer is out-of-page verification like Code Verify, which needs browser enforcement that does not exist). **Sensitive/business profiles must be desktop-only, cryptographically (`cloud:never`), not by toggle.** This is the cost of shipping a web app at all — Signal declines to; Proton/Bitwarden accept it and say so.
- **Revoked device retains MK + already-synced data until MK/CK_p rotation + re-encryption (accepted, sharpened).** And pre-rotation ciphertext survives in PITR/backups for the retention window ([backups](https://supabase.com/docs/guides/platform/backups), default up to 7 days). Cryptographic eviction "completes after N days" where N is your configured retention — surface that number in the UI, and set retention deliberately.
- **A fully compromised Edge Function is a full-database compromise.** The secret key is injected into `Deno.env` with no opt-out; scoped roles contain an SQL-injection-shaped bug, not arbitrary code execution. The defence is surface reduction + supply-chain control, and this must be an incident-plan assumption, not a contained risk.
- **Availability against a malicious server/relay is undefendable by definition.** It can withhold Yjs updates or drop rows; the freshness anchor buys *detection of rollback and gaps*, never *delivery*. Do not sell it as more.
- **Local desktop integrity = whatever the user's OS account can do.** Malware running as the user can swap the user-writable unpacked SQLCipher `.node` (perMachine:false) or call DPAPI to unseal the device secret — DPAPI binds to the OS user, not against code running as that user. State this next to the device-binding claim rather than implying more.

## 6. VERDICT

**Yes — this design can be made airtight enough to hold users' private data, but not as currently written.** The cryptographic core is genuinely good: the archiveContainer AAD discipline, the HKDF cross-IKM separation, the device-bound local key chain, the forward-secret ephemeral X25519, the row-AAD binding of `version`/`deleted`, and the correct base CSP set (`base-uri 'none'`, `frame-ancestors 'none'`, `'wasm-unsafe-eval'` not `'unsafe-eval'`) are all right and should not be traded away in the sync rewrite. The flaws are not in the primitives; they are in **who is trusted with the root key and who makes the release decision** — and every one of them is fixable because none of the sync code exists yet.

With B1–B12 and the REQUIRED set, the design meets or exceeds what Proton, Bitwarden and 1Password ship for the identical threat model. The honest boundary of "airtight" is three things the founder must accept in writing: the web app is weaker than the desktop and sensitive profiles must be desktop-only by cryptography; a weak human password is the floor of at-rest confidentiality under app-tier compromise; and availability against a hostile server cannot be guaranteed, only rollback-detected.

**What I would refuse to ship as designed, and why:**
1. **The auto-updater in its current state** — unsigned, silent, armed, verifying nothing (verified against source and the shipped artifact). This is live RCE the day the feed opens and it defeats every cryptographic control at once. Refuse until signed + Ed25519-pinned + user-driven (B1).
2. **MK in the browser** — one backdoored bundle or extension is the whole account forever, with no artefact left behind, and it is *not* one of the two accepted residuals. Refuse until MK is desktop-only (B2).
3. **Browser-side SAS confirmation without endpoint-identity binding** — a phishing lure walks the victim into handing MK to the attacker's tab while the design's own SAS reassures them. Refuse until consent moves to the desktop and names the attested account, with a commitment round under it (B2/amendment 3).
4. **aal2 presented as MFA without the RESTRICTIVE policy** — there is otherwise nothing to defeat, and the founder's entire "the web password is the accepted risk" calculus is void. Refuse until the policy exists (B3).
5. **The email-derived KDF salt** — a self-service email change bricks recovery and the native reset locks a user out of auth on the exact path they reach when in trouble. Refuse until the salt is random and server-held and the ceremonies are Nexus-owned (B5/B6).

Fix those five and land the rest, and "sve mora da bude airtight" is an honest description of everything except the three named residuals — which is exactly as airtight as this class of product gets.
