# Research: Zero-Knowledge Private Notes — Key Management & Unlock UX

**Domain:** how E2EE products handle key derivation, recovery, and unlock UX
without losing users' data or trust.
**Session:** 2026-07-04 (research phase 1, session 2).
**Nexus context:** private notes are zero-knowledge (`SEC-ZK`); recovery key
generated by default with informed opt-out (founder decision #6); re-auth
required to open the private section (`SEC-ZK-07`); PIN-protected local
accounts (`SEC-LOC`); web app is a launch surface.

## 1. Conclusions

1. **Zero-knowledge means the vendor cannot reset — and the whole industry
   says so out loud.** Bitwarden: no way to retrieve or reset the master
   password; if every fallback fails, the account is deleted
   ([Bitwarden help](https://bitwarden.com/help/forgot-master-password/)).
   Nexus copies this honesty: the UI states the deal plainly at setup, not in
   a support article after the loss.
2. **Separate "account recovery" from "data recovery" — Proton's model is the
   right one for Nexus.** Proton lets you reset the password via email/SMS
   (account access restored) but the E2EE data stays locked unless you have
   the recovery phrase, which doubles as an encryption-key backup
   ([Proton on data recovery](https://proton.me/blog/data-recovery-end-to-end-encryption),
   [recovery phrase](https://proton.me/support/recovery-phrase)). For Nexus:
   a cloud-account password reset restores everything **except private
   notes**; only the recovery key restores those. The reset flow must warn
   about exactly this at the moment of reset, and re-wrap keys when the
   recovery key is provided.
3. **The recovery kit should be a designed artifact, not an afterthought.**
   1Password's Emergency Kit — a PDF with account details, the Secret Key,
   and a blank for the password — is the pattern users actually manage to
   store ([1Password Emergency Kit](https://support.1password.com/emergency-kit/)).
   Nexus generates a "Recovery Kit" file at private-notes setup (default per
   decision #6), with save-confirmation or an explicit informed opt-out.
4. **Set up recovery contextually, not at registration.** The private-notes
   vault (and its recovery kit) is created when the user first opens the
   Private section — the moment they care — not as onboarding friction.
5. **Unlock UX follows the password-manager playbook:** vault stays unlocked
   for a configurable timeout, then re-locks; biometrics/PIN provide daily
   convenience while the real password stays strong; lock on device
   sleep/app minimize; per-platform timeout defaults
   ([Bitwarden vault timeout](https://bitwarden.com/help/vault-timeout/)).
   On Android, biometric unlock must be keystore-gated (`SEC-AND-01`), not an
   if-statement.
6. **Web E2EE is honestly weaker and we say so.** The browser gets its crypto
   code from our server on every load, so a compromised server could serve
   malicious JS — the classic "browser crypto" trust gap
   ([SecureDrop on browser crypto](https://securedrop.org/news/browser-based-cryptography/),
   [Cloudflare on JS trustworthiness](https://blog.cloudflare.com/improving-the-trustworthiness-of-javascript-on-the-web/)).
   Private notes remain available on the web app for parity, but the security
   docs (and threat model) rank desktop/Android above web; emerging
   code-transparency standards (WAICT-style manifests,
   [Mozilla 2026](https://hacks.mozilla.org/2026/05/trustworthy-javascript-for-the-open-web/))
   are a watch-item for later hardening.
7. **Argon2 is not in WebCrypto — plan the WASM path.** WebCrypto natively
   offers only PBKDF2 for password KDF; Argon2id (our `SEC-CR-04` floor)
   requires a WASM build (libsodium.js / argon2-browser)
   ([argon2-browser](https://github.com/antelle/argon2-browser),
   [libsodium pwhash](https://libsodium.gitbook.io/doc/password_hashing/default_phf)).
   Electron and Android use native libsodium; same parameters everywhere.
8. **1Password's two-secret model (2SKD) is worth knowing, not copying (yet).**
   Password + device-held Secret Key derive separate unlock and auth keys, so
   server-side cracking of the password alone is useless
   ([1Password security model](https://support.1password.com/authentication-encryption/),
   [deep keys](https://agilebits.github.io/security-design/deepKeys.html)).
   It complicates device enrollment UX; park it as optional post-v1 hardening
   (ADR note).

## 2. Landscape

| Product | Recovery model | Unlock UX | Lesson for Nexus |
| --- | --- | --- | --- |
| Bitwarden | None (self); enterprise admin reset; premium emergency contacts | Timeout + PIN/biometric quick unlock | Honest "we cannot reset"; fallback unlock paths on trusted devices |
| 1Password | Emergency Kit PDF + Secret Key (2SKD); family/org recovery | Biometrics; device-held Secret Key | Recovery kit as designed artifact; 2SKD as optional hardening |
| Proton | 12-word recovery phrase = key backup; account vs data recovery split | Standard login + session | The account/data recovery separation; SRP-validated phrase |
| Standard Notes | Master password only; conflicts duplicate, never merge | Per-app passcode options | E2EE limits server features; keep both on conflict |
| Obsidian Sync | User-managed E2EE password per vault | n/a (files local) | Per-scope encryption passwords are viable |

## 3. Nexus flows (proposed for the PRIV module PRD)

- **Setup (first open of Private section):** explain the deal in two
  sentences → derive keys (Argon2id → KEK, wraps random DEK per `SEC-CR-06`)
  → generate Recovery Kit (file download / printable, contains recovery key +
  account identifier) → user confirms "saved" or explicitly opts out through
  an "I accept the risk" step (decision #6). Optional on Android: enable
  biometric unlock now.
- **Unlock:** password prompt (or biometrics on Android); vault stays open
  for a configurable timeout (default: 5 minutes idle, lock on
  minimize/sleep; desktop and mobile defaults may differ); manual lock
  button always visible in the Private section.
- **While locked:** titles, previews, search results, and notifications from
  private notes are never rendered (`SEC-ZK-06`) — the section shows only a
  locked state.
- **Password change:** re-wrap DEK (no data re-encryption); Recovery Kit
  regenerate offered.
- **Cloud password reset without recovery key:** account restored, private
  notes remain locked; explicit warning at reset time; with recovery key —
  full restore and re-wrap.
- **Clipboard:** copying from a private note offers auto-clear of the
  clipboard after a short interval (password-manager pattern).

## 4. Expected feature checklist

Table stakes from the E2EE category: configurable auto-lock; biometric/PIN
quick unlock on trusted devices; recovery artifact at setup; honest no-reset
messaging; no plaintext in lists/notifications while locked; secure export
(encrypted by default per `SEC-DAR-02`). Differentiator: private notes as a
*section inside* a broader app with per-section lock — most competitors are
all-or-nothing vaults.

## 5. Pitfalls

- **Silent data loss at password reset** — the #1 UX failure mode; the reset
  flow must surface the private-notes consequence before the user commits.
- **Over-aggressive locking** kills daily use; defaults must be humane and
  configurable (Bitwarden community complaints are instructive).
- **Recovery-kit theater:** a checkbox "I saved it" that users click through.
  Mitigation: require re-entering a short segment of the recovery key at
  setup (verification), as several vendors do for recovery codes.
- **Crash reporters and logs** capturing plaintext or keys (`SEC-ZK-03`,
  `SEC-OPS-01`) — must be tested, not assumed.
- **Browser extensions/password managers** interacting with the private-notes
  unlock field; mark fields to suppress autofill where appropriate.

## 6. Open questions → PRD/architecture

1. Same account password for private-notes unlock (spec default) or optional
   separate passphrase? Recommendation: account password by default, optional
   separate passphrase as a setting (Obsidian shows per-scope passwords work).
2. 2SKD-style device secret as post-v1 hardening — ADR watch-item.
3. Clipboard auto-clear default duration (30s?) and whether it's opt-out.
4. Recovery-key verification strictness at setup (re-entry vs checkbox).
5. Web-app private notes: ship at parity with documented caveat (recommended)
   or desktop/Android-only until code-transparency matures — founder call in
   the PRIV module PRD.
